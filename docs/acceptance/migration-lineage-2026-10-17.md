用户选择保留本次验收的“启用的通知处罚规则全部满足后自动通知移送”。新事件继续调用原自动移送服务和停机补偿任务；没有启用规则或规则未通过时不自动发送。远端新增的告警已有授权入口校验保留，不能阻断原授权执行。旧内部待办和通知决定可读并按原入口办理，自动任务不修改、不代发。

## 已应用迁移重号

两条开发历史均已应用 `202610160001` 和 `202610160002`，但内容不同。原 SQL 文件只移动到独立扫描目录，文件名、内容和 Flyway 校验值保持：

`MigrationLineage` 按配置指定的 schema/table 只读检查历史脚本、校验值和成功状态，选择 `db/lineage/automatic` 或 `db/lineage/manual`；原人工通知的 PostgreSQL 触发器单独扫描 `manual-postgresql`。空库使用自动处置历史。未知校验值、混合历史、失败记录停止启动，不猜测、不执行 repair、不改历史表、不关闭校验。

追加 `202610170001` 在缺少结构时执行保留的原脚本，补齐自动处置所需字段/发送尝试表和历史通知决定结构，已存在的记录及启用时间不重建。追加 `202610170002` 仅补齐旧决定缺失的刷新触发器。原人工通知历史已到 `202610169001`、尚无融合查询索引 `202610160003` 时，只允许补应用这一项较早的迁移；其他较早待执行项阻断。应用后恢复正常顺序。

Spring Boot 使用 `MigrationConfiguration` 自动选择历史。独立 Flyway 调用升级既有库时，必须在 `load()` 前调用 `MigrationLineage.configure(configuration)`；不能直接把两个 lineage 目录都加到 locations。已有构建目录须移除搬迁前的两个旧编译资源，或使用干净构建，避免 Maven 资源复制遗留重号文件；源码原 SQL 不删除、不改内容。

## 验证范围

`MigrationLineagePostgresTest` 在显式配置的 `stage456_verify_*` 数据库随机 schema 验证空库、自动处置历史、原人工通知历史的升级及重复启动；逐项比较原 Flyway 历史，检查旧发送尝试与原通知启用时间保留，验证未知校验值和混合历史拒绝。自动移送矩阵、旧通知决定接口和 PostgreSQL 回归单独执行；实际结果以本次测试日志为准，不代表已部署其他机器或真实上级平台。
