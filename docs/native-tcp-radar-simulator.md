# 独立原生 TCP 雷达模拟器

2026-10-12：在现有信号模拟器增加一台独立 T02 TCP v3.0.0 模拟雷达，用于验证原生数据接入。实现位于业务前台仓库 `tools/device-simulator/tcp_radar.py`，页面为 `/tcp-radar.html`；不替换凌云 MQTT 雷达。

## 后台手动新增测试（2026-10-12 补充）

打开 `http://127.0.0.1:8766/tcp-radar.html`，默认页签为“后台手动接入测试”。原“登记并启动”位于“原有自动登记模式”，继续使用 15001 端口。

1. 在模拟器登录现有后台账号，核对测试经纬度，点击“启动独立 TCP 服务”。这里只监听 `127.0.0.1:15002`，不调用登记接口、不新增或改写设备；尚无平台连接时发送帧数应为 0。
2. 后台 **设备管理 → 接入设备 → 雷达**：自行填写一个未使用的设备编号、名称，选择所属单位/区域；数据来源选 **本机模拟测试**；设备地址 `127.0.0.1`，端口 `15002`，允许网段 `127.0.0.1/32`；雷达识别码引用留空，勾选 **采集 RTK、派生经纬度**。安装坐标可填写模拟器左侧位置。
3. 保存接入配置。预期生成一台新设备并保留模拟标识；实际连接成功后模拟器显示“数据登录成功”，航迹帧数逐秒增长。模拟设备在收到心跳/观测前不进入默认业务清单，保存结果不等于在线。
4. **设备实时监测**：选择刚才手动填写的设备，检查原生协议已连接、最新接收时间持续更新、RTK 与原始雷达航迹存在。健康未知不能解释成故障或伪造健康正常。
5. **设备接入调测**：选择同一设备，新建调测任务，执行连接检查、保存配置、开始调测并查看报告。报告以真实收到的数据和检查项为准，缺少健康或其他依据时如实显示待确认/未满足。
6. 返回模拟器点击“停止独立 TCP 服务”。后台应按实际连接状态变为离线/断开，旧样本与手动登记资料保留。再次启动只恢复同一端口监听，不重新登记设备；不要重复创建第二台指向同一端口的设备。

建议用时：启动与填表 2–3 分钟、监测核对 1 分钟、接入调测 2–3 分钟、停止与重连 1 分钟。原 MQTT 场景与 15001 模拟雷达具有独立状态、线程和停止入口；“停止全部收发”和模拟器进程退出仍停止所有模拟发送。

仅适用于后端和模拟器在同一台电脑。首次加载 Python 和 Java 更新需要重启相应服务；运行中的其他场景应先结束再加载。模拟器重启后重新登录，设备资料无需重建。

## 原有自动登记模式

1. 启动本机后台、管理端及信号模拟器，在模拟器使用现有后台账号登录。
2. 在模拟器顶部打开“TCP 雷达”，选择设备归属单位与区域，核对可编辑的演示经纬度。
3. 点击“登记并启动 TCP 雷达”。后台登记或复用 `QA-LOCAL-RADAR-TCP`，设备名称为“模拟 独立 TCP 雷达”，固定监听 `127.0.0.1:15001`。
4. 等待页面显示“已连接 · 数据登录成功”；到后台设备管理/设备实时监测查看该设备的原生协议状态、RTK 和雷达航迹。发送计数只证明模拟器发出，验收以后台实际保存的报文及航迹为准。
5. “停止 TCP 雷达”只停止此 TCP 对端。地图“停止全部收发”同时关闭它。服务重启或登录失效后不自动续发，需重新显式启动。

MQTT 场景的设备、来源、主题、批次、启动入口均保持原样。TCP 使用独立端口、线程和登记身份；停止 TCP 不停止 MQTT。新模块首次加载需要重启后端和模拟器，若原场景正在运行，应先安排加载时机。

## 接口与边界

- 新增 `POST /api/v1/local-interface-simulator/radar-device`。请求为 `owner_org_id`、`district_id`、`longitude`、`latitude`、`coordinate_system`（`WGS84` 或 `WGS-84`，2026-10-20 起必填且拒绝其他坐标系），要求 `Idempotency-Key`，沿用 `{ok,data,error}` 与字符串 ID。
- 仅启用 `local+qa` 或隔离 `test`、且 `app.qa.device-setup.enabled=true` 时注册；生产 profile 始终禁用。服务端检查后台身份、`interfaces.op`、`devices.op`、`devices.auth` 和全局范围，所属单位/区域必须有效。
- 同一身份重复登记返回已有设备；登记按所属单位行加事务锁，数据库来源唯一约束兜底。来源、范围、连接配置冲突或设备停用时拒绝覆盖；再次启动不移动已登记的位置。
- 来源为 `live`（实际 TCP 传输）且 `simulated=true`，成功登记审计为 `local_qa_device_prepare`。上线和状态仍来自实际协议接入；不写验收数据库、不启用 dev-seed。
- 手动模式新增模拟器 `GET /api/tcp-radar/manual/status`、`POST /api/tcp-radar/manual/start` 和 `/stop`；start 仅接受经纬度，并通过只读会话校验后监听端口。后台仍由用户显式提交 `POST /api/v1/devices/onboard`，追加可选布尔字段 `simulated`（省略/false 维持真实接入）；只有明确 true 才创建模拟来源及成功登记审计，且与设备登记保持同一事务。
- `GET /api/v1/devices/onboarding-options` 返回 `manual_radar_simulation_allowed`。服务端检查模拟环境、QA 开关、后台身份、原有操作权限和全局范围；此模式只允许本机 TCP 雷达。真实 TCP 雷达和四通道反制接入保持原路径，生产拒绝模拟声明，编辑不能改变来源性质。
- 协议使用大端帧、CRC16-MODBUS、DATA 登录、心跳应答、只读寄存器、RTK 订阅和每秒一帧航迹；只有登录通过后才发送模拟无人机航迹。无重启、反制或其他控制指令。
- 使用独立启动会话和递增帧号，支持 TCP 拆包/粘包、断线重连；端口占用、CRC 错误、权限失败及会话失效明确报错。
- RTK 样本按设备和连接会话内的报文键去重，原始线帧号单独保留；设备重新启动后帧号复用不会覆盖旧样本。追加迁移 `V202610129002__radar_rtk_session_identity`，历史样本不补造连接身份。
- 不提供协议文档未明确的健康正常/告警清除依据。连接在线不代表健康正常或异常处置已恢复。相对站址高度不冒充 AGL/AMSL。
- 本轮保留原始协议航迹，不将模拟 TCP 来源送入实测 `live-radar:` 统一目标通道；即使实测提升开关开启也拦截。生产环境不连接已登记的模拟 TCP 设备；真实 TCP 设备路径保留。

## 验证

### 2026-10-12 监测与调测并发连接修正

原模拟器在接受持续采集连接后同步处理该连接，无法及时接受端口探测和协议调测的新连接，可能导致连接被拒绝或登录超时。两个 TCP 模式现均使用独立客户端处理线程，每个监听实例最多处理 8 个客户端；登录、解码缓冲区、RTK 订阅各自隔离，发送帧号并发分配，不因调测连接断开把仍在采集的会话显示为未连接。

停止服务、平台登录失效或账号切换会关闭本实例的全部客户端。仅关闭一个调测连接不影响持续采集。手动模式仍不自动登记设备，两个端口与 MQTT 场景保持原有隔离；真实设备是否支持多个客户端仍须按厂家协议验证，本修改只调整本机模拟器。

`python -m unittest discover -s tests -p 'test_tcp_radar*.py' -v`：18 项通过，包含原 13 项与新增 5 项并发回归；覆盖原有/手动两种模式、随机端口、监测加短连接探测再调测、无效登录隔离、停止和重新启动、会话失效/替换、连接上限。新增用例在旧实现上先复现失败，再验证修复通过。

正式测试：`LocalQaRadarApiTest`、`LocalQaRadarPostgresTest`、`LocalQaDeviceGateTest`，以及模拟器 `tests/test_tcp_radar.py`。数据库测试使用专用 `plan_filing_verify_*` 库的随机 schema；不使用运行业务库。

真实雷达连线、实测探测性能、设备故障恢复与现场坐标标定尚未验证，本次结果只能作为模拟协议接入结果。
