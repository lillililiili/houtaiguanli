# 系统管理接口

系统管理接口统一使用 `/api/v1`、JSON `snake_case` 和 `ApiResponse`。登录后的请求携带 `Authorization: Bearer <session_id>`；写操作携带 8–128 位 `Idempotency-Key`，修改或删除已有对象同时提交当前 `expected_version`。重复键但参数不同、或版本落后均返回 `409`。

账号分为 `FRONTEND`（前台用户）和 `BACKEND`（后台用户）。前台用户分配自定义业务角色；后台用户使用固定内置身份 `ROLE-BACKEND`，无需配置角色菜单，拥有全部后台菜单及管理功能。唯一超级管理员 `ROLE-ADMIN` 也属于后台用户，其角色、状态及全部单位范围不可修改，不可删除、转移或分配给新用户。超级管理员的直接反制仍须显式 OP 授权。

`user_type` 由服务端根据持久化角色身份返回：只有 `ROLE-ADMIN`、`ROLE-BACKEND` 为 BACKEND，其余为 FRONTEND。存量自定义角色用户均保留为前台用户，不因历史后台菜单授权自动升级。新增迁移 `V202610080002` 只登记固定后台角色及后台所需读取/管理动作，不创建账号或演示数据，不授予申请、审批、执行、直接反制等业务动作。

## 认证与权限

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/auth/login` | 登录，返回数据库会话 ID 与过期时间；管理端提交 `client_type=BACKEND` |
| GET | `/auth/me` | 用户、`user_type`、角色、`menu_keys`、原子权限码、权限版本、`data_scope`（见下）和资料 `version`；仍返回内部 `scope_mode` |
| PATCH | `/auth/profile` | 本人修改姓名、电话（`name`、`phone`、`expected_version`），返回更新后的 `/auth/me`；不撤销会话，审计 `profile_updated` |
| POST | `/auth/logout` | 注销当前会话 |
| POST | `/auth/change-password` | 修改密码并撤销该用户全部会话 |

会话令牌只由前端保存在 `sessionStorage`，“记住账号”只保存账号。首次登录待改密用户只能访问当前用户、退出和改密接口。密码重置、停用、账号类型变化、角色变化、数据范围变化、角色权限变化都会撤销受影响用户的旧会话。

管理端每次请求携带 `X-Client-Type: BACKEND`。前台账号即使密码正确也不能在后台登录，返回 `403 BACKEND_ACCESS_DENIED`，不创建会话，并记录独立失败审计；用前台会话访问管理端同样拒绝。后台专属接口另有服务端身份守卫，移除或伪造客户端标识不能绕过。共享业务读取接口保留原有角色、动作和数据范围校验。

本人可改的资料只有姓名和电话（电话只能含数字、空格和 `+ - ( )`）；所属单位、账号类型、角色、数据范围由后台用户在用户管理里调整。改密时当前密码输错返回 `400 CURRENT_PASSWORD_INCORRECT`，不是 `401`，前端停在原表单提示，不退出登录；输错与登录失败共用 `fail_count` 和锁定，失败计数和 `password_change_failed` 审计在独立事务提交。达到上限后返回 `429 PASSWORD_ATTEMPTS_LOCKED`，锁定期内改密和重新登录都被拒绝，当前会话不受影响。只有 `401` 才表示会话失效（ZT-28）。

两个前端收到会话失效的 `401` 时（登录、退出接口自身的 `401` 除外）不再直接跳登录页：在当前页面弹出“登录已过期”，用同一账号输入密码就地重新登录，页面、打开着的表单和已填内容都保留；被拒的是提交时说明“刚才的提交没有保存”，重新登录后再提交一次。没有业务页面可保留时（如首次改密页）回登录页并提示登录已过期（ZT-29）。个人资料入口：管理端右上角菜单“个人资料 / 修改密码”，业务前台右上角菜单“个人信息 / 修改密码”。

权限等级为 `NONE < READ < OP < AUTH`，**模块码**返回形式为 `{permission_code}.read|op|auth`；**动作码**（形如 `disposal:approve`）返回**原文**，等级 ≥ READ 即下发（直接反制仅显式 OP）。前台工作台固定可见；前台菜单入口只有在 `menu_enabled=true` 且权限至少为 `READ` 时返回。后台菜单由固定后台身份提供，不使用自定义角色的菜单矩阵。数据范围见下节；仅调整前台业务角色时不改写已有范围。

## 用户、组织与区域

| 资源 | 接口 |
| --- | --- |
| 用户 | `GET /users`（`keyword/status/roleCode/user_type/orgId/page/size`；类型筛选在分页前，`orgId` 含该组织及其下级）、`POST /users`、`GET/PATCH /users/{id}`、`PUT /users/{id}/status`、`POST /users/{id}/reset-password`、`PUT /users/{id}/access` |
| 组织 | `GET/POST /organizations`、`PATCH /organizations/{id}` |
| 行政区域 | `GET/POST /districts`、`PATCH /districts/{id}`、`PUT /districts/{id}/status` |

新增用户一次提交账号、资料、用户类型、前台业务角色（后台无需选择）和 6–32 位复杂临时密码；创建后强制首次改密。`PATCH /users/{id}` 一次提交姓名、电话、组织、可选用户类型、角色及 `data_scope`，不要求填写操作原因。创建与权限修改审计由服务端按真实操作者区分“超级管理员直接…”和“后台用户直接…”。纯数字或不满足复杂度的临时密码返回 `400 PASSWORD_POLICY_VIOLATION`，不创建用户；临时密码只保存哈希，明文和哈希都不进入响应或审计。用户接口不接收也不返回 `scope_mode` / `scope_grants`，数据范围统一用 `data_scope` 表达。

2026-10-08：以上用户维护操作向全部后台用户开放，成功审计记录真实操作者。用户列表、详情、创建及更新响应包含 `user_type`。新建时省略类型默认为 FRONTEND，并必须指定可用自定义 `role_code`；BACKEND 不要求业务角色，传入角色时只允许 `ROLE-BACKEND`。编辑省略类型则保持原类型；改为后台自动使用固定角色和 ALL 范围，改回前台必须指定自定义业务角色，省略范围时恢复 OWN_ORG。类型与角色不一致返回 400，类型变化与角色变化一样撤销全部旧会话。旧 `/access` 仅用于前台业务角色调整，不能把后台账号改成自定义角色；类型切换统一走资料 PATCH。后台账号可以创建、停用及重置密码，唯一超级管理员的既有保护不变。

### 账号数据范围（ZT-14，2026-10-06）

| `data_scope` | 页面文字 | 能看到的业务数据 |
| --- | --- | --- |
| `ALL` | 全部单位 | 全部单位、全部区域（后台用户固定为此项，不能改） |
| `OWN_ORG` | 本单位 | 账号所属单位的数据。**新建前台账号不填时的默认值** |
| `OWN_ORG_TREE` | 本单位及下级单位 | 所属单位及其全部下级单位（按组织树 `parent_id`）的数据 |
| `CUSTOM` | 指定单位和区域（只读） | 历史上逐条授权“单位 + 区域”的存量账号，原样保留；接口不能新设，只能改成上面三种 |
| `NONE` | 不能查看业务数据（只读） | 存量无范围账号，原样保留 |

`POST /users` 与 `PATCH /users/{id}` 只接受前三种，其他值返回 `400 VALIDATION_ERROR`；改超级管理员的范围返回 `400 SUPER_ADMIN_PROTECTED`。存储上 `本单位/本单位及下级` 落为 `scope_mode=ASSIGNED` 加 `app_user.scope_org_rule`，服务端把它展开成 `app_user_data_scope` 元组（所属单位或其子树 × 全部区域），业务接口沿用原有的“单位 + 区域”元组过滤，没有另写一套判断。新建组织、组织换上级、新建区域、账号换单位时同一事务重建；服务启动时再按当前组织树核对一遍。元组只落在所属单位子树内，元组陈旧最多少看、不会多看。改数据范围或给按单位维护范围的账号换单位，都按权限变更撤销该账号旧会话（审计 `user_data_scope_changed`）。区域停用检查只统计手工授权元组，按单位维护的元组不阻止停用区域。

按范围收窄的接口（列表、详情、统计、导出同口径，越权按 ID 访问返回 404 或 403）：告警与无人机事件（`/alarms`、`/alarms/export.csv`、`/uav-events`）、目标与轨迹、合法性研判与复核、飞行计划与航线、空域、机场、风险与空间风险、设备与设备运维/调测/监测、处置授权、业务交接、处罚案件、证据文件与证据台账（含 `/content`、`/preview`、导出）、运行统计与报表（`/stats/**` 的单位下拉、查询、CSV/XLSX 导出）、数据大屏与工作台汇总、单位档案/联系人/预案、天气风险与本地接口配置中按单位归属的数据。实时推送 `/realtime` 只发主题和时间，不带业务数据，前端收到后重读上述接口，所以重读同样按当前账号范围收窄。

不按单位收窄：后台系统管理（用户、角色、组织树、区域、审计日志）、地图包管理、MQTT 接入列表等全局技术配置，以及登录、个人资料和改密。后台专属配置要求后台身份；后台固定 ALL 范围。共享业务数据接口继续校验单位及区域，保留自动规则、单位档案等全局操作的既有范围守卫。

用户管理页面为左侧组织树、右侧用户列表；点击组织按该组织及其下级筛选用户。修改用户资料时可同时调整角色，更多菜单不再单独提供权限入口。组织可在树中新增、编辑，不提供停用或删除接口；存量停用组织由迁移统一恢复为启用。新增组织只需名称和上级，`org_code` 由服务端自动生成，创建后不可改。行政区域在用户页头“区域管理”里查看、新增和改名（新增、改名需 `users.auth`），区域编码创建后不可改；停用区域会影响数据范围，页面不提供，仍只能通过接口。禁止通过任何用户接口修改唯一超级管理员的角色或状态。

## 自定义角色

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST | `/roles` | 列表；或一次提交名称、说明和完整权限矩阵创建角色。原因可省略，服务端写入固定审计说明 |
| GET/PATCH | `/roles/{role_code}` | 详情；或按 `expected_version` 修改自定义角色说明 |
| GET | `/permissions/catalog` | 权限目录 |
| PUT | `/roles/{role_code}/permissions` | 按 `expected_version` 和完整矩阵立即更新权限。原因可省略，服务端写入固定审计说明 |
| DELETE | `/roles/{role_code}?expected_version=...` | 请求体提交原因，立即删除未被用户引用的自定义角色 |

自定义角色可配置前台业务模块的 `READ/OP/AUTH`，菜单开启时同模块权限至少为 `READ`。后台菜单不再提供配置，后台专属动作也不在前台角色页面展示。历史完整矩阵继续兼容保存，但不能绕过后台身份守卫。角色权限改变后，该角色所有用户的权限版本增加且旧会话立即失效。仍被用户引用的角色不能删除。

2026-10-09：角色页动作权限统一使用“无／允许”单选，保存时分别提交 `NONE/OP`。普通动作的历史 `READ/OP/AUTH` 均显示“允许”，保存为 `OP` 并保留原有动作授权；直接反制仍只有显式 `OP` 显示并保存为“允许”，其他等级按“无”处理。前台设备模块拆为“查看设备”和“控制设备”两项单选，仍映射既有 `devices` 模块等级：仅查看为 `READ`、允许控制为 `OP`、均不允许为 `NONE`；允许控制同时允许查看，取消查看同时取消控制，编辑时不开启后台设备菜单。菜单权限等级及服务端授权契约保持不变。

`GET /permissions/catalog` 与角色详情仍返回完整矩阵，写接口仍要求完整矩阵。编辑前台菜单时未展示项原值随请求保留，新角色未展示项初始化为 `NONE/false`；历史后台菜单授权不再赋予后台访问资格。`statistics/stats` 在自定义角色中只配置前台统计入口，后台报表随后台身份固定开放。角色页面不列出固定 `ROLE-BACKEND`，保留超级管理员只读展示。动作页单列“前台设备操作”，配置共用 `devices.read/op`，用于前台设备读取与控制，不开启后台设备菜单，也不替代反制动作、对象、范围和安全条件校验。

## 审计日志

`GET /audit-logs` 支持 `from/to/account/module/action/result/objectType/objectId/page/size`；`GET /audit-logs/{audit_id}` 查询详情；`GET /audit-logs/export.csv` 使用相同条件导出，最多 50,000 条。日志只读，不提供修改、删除、附件或虚构的归档策略接口。CSV 对公式前缀做安全处理，密码与令牌不记录。

角色删除和用户逻辑删除等敏感操作必须填写原因；新增用户、新增自定义角色、保存角色权限以及通过资料编辑调整用户角色不要求手工填写原因，由服务端自动生成审计说明。服务在同一事务内完成变更和成功审计，失败尝试也按服务端安全策略留痕。

## 初始化与恢复

本地 `local` profile 默认不开演示种子：库里还没有账号时，启动会一次性建唯一超级管理员 `admin1 / Admin@2026dev`（`app.bootstrap-admin`），首次登录强制改密；显式打开演示种子（`APP_DEV_SEED_ENABLED=true`）才建 `admin1 / changeme` 合成账号。共享环境关闭 Seeder，通过 `APP_BOOTSTRAP_ADMIN_ENABLED=true`、`APP_SUPER_ADMIN_ACCOUNT`、`APP_SUPER_ADMIN_NAME` 和 `APP_SUPER_ADMIN_PASSWORD` 一次性初始化。初始化后删除密码并关闭开关，但保留账号变量用于启动完整性校验。

忘记超级管理员密码时，运维人员在服务器环境设置 `APP_SUPER_ADMIN_RECOVERY_ENABLED=true` 和 `APP_SUPER_ADMIN_RECOVERY_PASSWORD`，并以非 Web 模式启动。恢复会重置密码、强制改密、撤销会话、记录脱敏审计并自动退出；没有网页恢复接口。

### 空库准备（不开演示种子）

新装系统只靠管理端页面即可准备好，按顺序：

1. 新建的 PostgreSQL 库先执行 `CREATE EXTENSION postgis`，再启动后端完成迁移；按上一段一次性建出唯一超级管理员，登录后按提示改密。
2. 用户管理 → 左侧单位树“新增”：至少建一个单位。
3. 用户管理 → 页头“区域管理” → “新增区域”：填区域名称和区域编码。设备、连接和数据范围都按“单位 + 区域”归属。
4. 接口配置 → 设备数据连接 → “新增连接”：选所属单位 / 区域。正式环境只有“真实设备”，启用前须填用户名和 `env:` 凭据引用；显式测试环境（`local`+`qa`）还可选“模拟回放”，并可一键填入本机模拟器默认值（`local-lingyun-replay`，`127.0.0.1:1883`，仅回环）。新连接默认停用，确认后点“启用”。
5. 规则管理 → 研判规则集：没有生效版本时系统不会自动研判。对已发布的版本点“启用此版本”并填写原因（记审计）。演示参数版本（`LEGALITY-DEMO`、`SPACE-RISK-DEMO`）只在显式测试环境可启用；正式环境要等业务方确认参数、由开发以迁移发布正式版本后再启用。

唯一超级管理员固定拥有全部动作权限（直接反制除外，仍须显式 OP 授权）。服务端判权不依赖演示种子插入的授权行，空库上同样能完成以上操作。
