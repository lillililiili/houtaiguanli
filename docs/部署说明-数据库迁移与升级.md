# 部署说明：数据库迁移与升级

面向部署与运维。每条都标出处（决策号或验收文档），照着做即可；有疑问以出处为准，不要凭经验改写迁移文件。

## 1. 迁移文件放在哪、什么时候加载

| 目录 | 加载时机 | 放什么 |
| --- | --- | --- |
| `server/src/main/resources/db/migration` | H2 与 PostgreSQL 都加载 | 建表、列、索引、CHECK 等两种库都能跑的 DDL |
| `server/src/main/resources/db/postgresql` | **只有 PostgreSQL 加载** | PostGIS 几何约束与 GIST 索引、只增/接替触发器、PG 专属的一次性数据订正 |

配置出处：主配置 `application.yml` 的 `spring.flyway.locations` 同时列出两个目录（生产是 PostgreSQL）；
测试配置 `application-test.yml` 只列 `db/migration`，所以 H2 不会加载 PG 专属文件。

**含义**：只在 PG 上成立的语句（触发器、`ST_*`、`DISABLE TRIGGER`）必须放 `db/postgresql`，
放进 `db/migration` 会在 H2 测试上直接把服务启动打挂。

## 2. 版本号规则

- **自阶段 10 起，B 线新迁移按实际日期编号 `V2026MMDDnnnn`**（决策 10-14），不再沿用 `20260905` 固定前缀。
  根因：固定前缀永远小于协作者 A 的日期编号，两条线并行时顺序必然错乱。
- 已提交的历史编号（`V202609050xxx`、`V202609050073_5`）**不重新编号**（决策 10-17）——重编号会让所有已迁移的库校验和失配。

## 3. 乱序（`out-of-order`）

- **只有 `local` profile 放开**（决策 10-10 修订）：`application-local.yml` 里 `spring.flyway.out-of-order: true`，
  注释写明原因（A 的 `V202609050001` 编号低于本地库已应用版本）。
- **主配置与生产保持 Flyway 缺省的严格顺序**。全新库按版本序执行，不存在乱序问题。

## 4. 生产首次部署

**从全新库开始**（决策 10-17）。按版本序执行全部迁移，不需要任何豁免开关。

## 5. 已有库的升级

### 5.1 已迁到 `202609070001` 之后的非 local 库

这类库（开发库、验收库）会遇到"新迁移的版本号低于已应用版本"。**一次性**使用下列之一，
**验证通过后立即撤回，不要留在配置里**（决策 10-17）：

- `spring.flyway.ignore-migration-patterns`（推荐：范围可控），或
- 临时打开 `spring.flyway.out-of-order`。

### 5.2 迁移 061 被改过的库需要 `flyway repair`

提交 `31f9ece`（用户的另一个会话）修改了**已提交**的迁移 061（去掉两条 UPDATE），H2 与 PG 的校验和都随之改变。
按旧 061 迁移过的库启动时会报校验和失配，需要先 `flyway repair` 再启动。
出处：`docs/backend-stage85/acceptance.md` 的"工作区外部改动说明"。

> 教训：**不要修改已提交的迁移**。需要订正就新增一条迁移。

### 5.3 `V202609050073_5__stage10_airspace_kind_code_renormalize.sql` 是一次性订正，禁止照抄

它临时摘掉 `airspace_version` 上的用户触发器，把存量的 `HEIGHT_LIMIT` / `TEMPORARY` 归一成五值字典，
再恢复触发器（决策 10-13），**只为把历史库救回来**。

- 新库不需要它（种子自阶段 10 起只写五值，迁移 074 的 CHECK 兜底）。
- **不允许再写第二个这种迁移**：摘触发器期间，只增/接替式约束对任何并发写入都不生效。
- 迁移 074 只做 `DROP CONSTRAINT` + 重建五值 CHECK，**不含 UPDATE**（决策 10-5）。
  若某个库仍有旧值行，`ADD CONSTRAINT` 会以 PostgreSQL 的 `is violated by some row`（SQLSTATE 23514）明确失败——
  这是刻意的：数据订正要显式做，不能由约束迁移悄悄改写业务数据。
  失败时按 5.3 的方式归一后重跑迁移。

## 6. PostgreSQL 专项测试

- 环境变量：`POSTGRES_TEST_URL`、`POSTGRES_TEST_USER`、`POSTGRES_TEST_PASSWORD`。
- 库名规则：`stage456_verify_*`（阶段 4/5/6 起沿用至 8.5/9/10）、`stage2_target_verify_*`。
  验收库另用 `uav_stage{N}_verify`。
- PG 专项用例（如 `Stage9PostgresTest`）**关掉 Spring 的 Flyway**（`spring.flyway.enabled=false`），
  自己在随机 `stage456_` schema 上手动跑 Flyway（含 `db/postgresql`），跑完只删本 schema。
  因此它们不会污染同一个库里的其他数据。
- **用完即弃，不要复用验收库跑测试**：验收库要留作升级路径的证据。

> 常跑 PG 回归清单（决策 12-16）：`Stage85/9/8/7/5/4PostgresTest`、`PostgresStage2CompatibilityTest`、`FlightReadPostgresApiTest`、`AirspaceReadPostgresApiTest`、`MqttP1PostgresTest`（库 `stage456_verify_*`）+ `TargetReadPostgresApiTest`（库 `stage2_target_verify_*`）。

> 阶段 13（决策 13-16）：`app.disposal.expiry.enabled` 缺省关、local 开；生产建议打开（到期任务只做状态卫生，执行时限的安全闸门在执行接口本身）。

- 2026-09-08（阶段 13）：本地/测试环境的阶段 8 回放种子改为"已灌过即跳过"。此前若库由 `1692e10` 之前的构建灌过回放数据集，新构建启动会报 `SOURCE_MESSAGE_CONFLICT: lingyun:radar:S85R1#0`；升级后不再重灌，库里保留旧数据集产物。要用新数据集演示，请换一个空库。
