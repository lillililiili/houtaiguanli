# 全系统 WGS-84 坐标一致性审查

审查日期：2026-10-20（按会话日期）。

结论：系统主链路以 WGS-84 为约定，数据库空间列主要使用 EPSG:4326，经纬度主要采用十进制度、几何数组采用 `[经度, 纬度]`。但入口和消费端没有完全统一执行该约定，发现 4 项需修正的问题，因此不能认定为“整个系统均已严格统一”。

用户在本轮补充“好像是 WGS-84”，本报告据此检查 WGS-84 一致性；不是 CGCS2000 改造或中国国家标准符合性认证。WGS-84 的官方定义见 [NGA](https://earth-info.nga.mil/index.php?action=wgs84&dir=wgs84)，GeoJSON 的十进制度和经度在前约定见 [RFC 7946 §3.1.1、§4](https://www.rfc-editor.org/rfc/rfc7946)。

## 需修正的问题

### 1. P1：设备坐标系允许自由写入，融合感知直接当作 WGS-84 使用

后端 `DeviceController.java:254、266` 把请求的 `coordinate_system` 传入服务；`DeviceService.java:581-586` 只检查坐标成对与数值范围，`:621` 原样保存任意非空坐标系名称。`V3__device_operations.sql:30-52` 同样没有坐标系白名单约束。

业务前台 `src/services/situationData.js:337-360` 的 `toDevices()` 仅检查是否可以转成有限数字，没有校验坐标系或经纬度范围，随后丢弃坐标系信息。融合感知通过 `src/pages/situation/situationApiSource.js:277-291` 调用该函数；公共地图 `public/assets/js/map.js:505-515` 按 WGS-84 投影。

相反，管理端 `ruoyi-ui/src/services/deviceLocationMap.js:43-49` 拒绝非 WGS84/WGS-84 的点。因此同一条设备资料存在业务图可画、管理图不可画的路径；如果传入的是 GCJ-02 数值，就可能被画到错误位置，相关设备范围也会跟随错误中心。

实测当前 `toDevices()`：

| 输入 | 实际输出 |
| --- | --- |
| `118.3,37.2,WGS84` | `posValid=true` |
| `118.3,37.2,WGS-84` | `posValid=true` |
| `118.3,37.2,GCJ02` | **仍为 `posValid=true`** |
| `118.3,37.2,CGCS2000` | **仍为 `posValid=true`** |
| `201,37,WGS84` / `118,95,WGS84` | **仍为 `posValid=true`** |
| 缺经度 | 正确排除 |

越界案例证明消费端缺少防御校验，不表示当前后端能写入该越界值；后端已有范围检查。非 WGS 坐标系漏检则贯穿上述设备写入与页面消费路径。未向运行系统提交这些异常数据。

建议：接入边界只接受明确支持的 WGS-84 表达并规范化；其他基准拒绝或走有依据的转换流程。地图统一复用严格坐标校验，未知坐标不能参与设备覆盖定位。

### 2. P1：空域几何中显式的其他坐标系会被忽略并标成 4326

`GeoJsonParser.java:53、170-174` 只检查 FeatureCollection 根对象的 `crs`；空名称被视为通过，名称还使用 `contains("CRS84")`、`endsWith("4326")` 宽松匹配。Feature 或 geometry 内的声明没有检查，`:133` 直接生成 `SRID=4326`。

`AirspaceWriteService.java:240-246` 把请求的 `boundary` 包装进新 FeatureCollection，边界自己的 CRS 因此位于 geometry 层，能够触发该遗漏。这是实际空域创建/更新路径，不只是假设的未使用解析工具。

以当前源码独立编译解析器，使用相同三角形坐标执行 7 个探针：

| 声明位置/内容 | 实际结果 |
| --- | --- |
| 不声明 CRS | 正确按 GeoJSON 默认接受 |
| 根对象标准命名 CRS 为 EPSG:4326 | 正确接受 |
| 根对象标准命名 CRS 为 EPSG:4490 | 正确返回 `CRS_NOT_SUPPORTED` |
| 根对象 `crs` 为字符串 `EPSG:4490` | **接受并标为 4326** |
| Feature 内声明 EPSG:4490 | **接受并标为 4326** |
| geometry 内声明 EPSG:4490 | **接受并标为 4326** |
| 根对象名称为 EPSG:14326 | **后缀匹配通过并标为 4326** |

赋 SRID 只是在声明基准，并未完成坐标转换。PostGIS 对 4326、几何合法性和范围的约束无法识别已被错误贴上 4326 标签的数值。此处可能影响空域位置及依赖该边界的研判。

建议：对接受的声明做精确白名单检查，显式冲突、结构错误和不支持的坐标系应拒绝；对业务接入支持的所有层级检查冲突。无 CRS 的标准 GeoJSON 仍按其默认 WGS-84 处理，不要求无意义的额外字段。

补充静态发现：`LocalRouteInputService.java:142-153` 检查 LineString 类型与数值，但没有处理几何内显式 CRS 后就生成 4326；本地模拟航线入口也应纳入同一修正。此分支未单独动态调用，不作为新增独立问题计数。

### 3. P2：缺失坐标可能被转成真实的 0°

业务前台 `src/services/positionMap.js:16-21` 的 `coordOf()` 先执行 `Number()`，没有先拒绝 `null`、空字符串等缺失值。该工具用于目标位置、反制目标地图等路径（例如 `src/pages/alarms/CounterLaunch.vue:57`、`AuthorizationTargetMap.vue:20`）。

直接执行当前函数，结果：

- `{longitude:118.3,latitude:37.2,coordinate_system:'WGS84'}` 正确返回原位置。
- 经度 `null`、纬度 `37.2`，返回 **`{lon:0,lat:37.2}`**。
- 经度 `118.3`、纬度空字符串，返回 **`{lon:118.3,lat:0}`**。
- 两者均 `null`，返回 **`{lon:0,lat:0}`**。

这是异常数据到达该函数时可复现的消费端缺陷，未证明当前正常后端已输出上述缺失位置对象，也未声称当前地图已经出现零点。

建议：转换前验证类型、非空及成对完整，再检查有限数与范围。合法的真实 0°仍应允许；不能用统一禁止 `(0,0)` 代替缺失校验。

### 4. P2：WGS84 与 WGS-84 的等价写法在任务设备检查中不兼容

`DeviceService.java:621` 允许原样保存 `WGS84`。管理端地图同时接受 `WGS84`、`WGS-84`，但 `FlightDeviceCheckService.java:166-168` 只接受精确的 `WGS-84`。

`:99` 对不满足该条件的设备增加无法检查数量并跳过覆盖检查。因此同一台有合法位置、坐标系写作 `WGS84` 的设备，可在地图定位，却在任务检查被当成位置未知。当前常规表单通常写入 `WGS-84`，所以这个问题不等于全部现有设备都受影响。

建议：在写入时规范化等价名称，读侧兼容已有等价写法。禁止把其他坐标基准作为别名兼容。无需改写历史冻结材料。
