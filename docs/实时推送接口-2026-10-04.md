# 实时推送接口（2026-10-04）

用户要求融合感知以外的页面也实时接收数据，并选定“后端推送”方案。本接口只推送“哪类数据变了”，不推送业务数据；页面收到信号后经原有接口按当前筛选、分页和权限重读。

## 接口

`GET /api/v1/realtime/events`，`Accept: text/event-stream`，`Authorization: Bearer <session_id>`。未登录返回 401（`{ok:false}` 包装），连接数超过 `app.realtime.max-connections`（默认 200）返回 503 `REALTIME_BUSY`。

| 事件 | data | 说明 |
| --- | --- | --- |
| `ready` | `{"listening":true,"at":<epoch ms>}` | 连接建立；`listening=false` 表示数据库监听未启用（非 PostgreSQL 或 `app.realtime.enabled=false`），只有心跳 |
| `change` | `{"topics":["alarm","target"],"at":<epoch ms>}` | 有变化的数据类别；`"*"` 表示后端监听重连后需全部重读（前端按恢复处理，见下文“连接恢复”） |
| 注释 `:ping` | — | 每 `app.realtime.heartbeat-millis`（默认 20 秒）一次，保持代理连接 |

连接在 `app.realtime.stream-timeout-millis`（默认 30 分钟）后结束，前端重连并重新鉴权。响应带 `X-Accel-Buffering: no`，Nginx 不缓冲。

页面关闭、刷新或前端主动断开时，后端下一次写心跳或信号会收到“客户端已断开”（`AsyncRequestNotUsableException` / `ClientAbortException`）。这是正常断开，`GlobalExceptionHandler` 只记 DEBUG（`Client disconnected on <path>`），不再记 ERROR、不写审计；其他异常照旧记 ERROR（OBS-09）。

## 信号来源

迁移 `V202610059001__realtime_data_change_notify.sql`（`db/postgresql`）为业务表建语句级 INSERT/UPDATE/DELETE 触发器，借助转换表只在确有行变化时 `pg_notify('app_data_change', <topic>)`。信号随事务提交送达，回滚不发；应用、模拟器受控 seed 和手工 SQL 的写入都会产生信号。`DataChangeListener` 用独立连接 `LISTEN`，按 `app.realtime.flush-millis`（默认 300 ms）合并后经 `RealtimeHub` 分发。

| topic | 表 |
| --- | --- |
| `alarm` | alarm、alarm_escalation（告警升级记录，2026-10-06 `V202610069132` 接入）、uav_event、uav_event_verification/advisory/voice_advisory |
| `target` | target、target_latest_state、target_source_link、target_track_status、track_point、ops_target_latest_state、ops_track_point、sensing_target |
| `legality` | legality_review、legality_review_history、assessment_result、alarm_merge_member |
| `risk` | flight_risk、flight_risk_verification、space_risk_fact、weather_risk_fact、risk_clearance_evidence |
| `plan` | flight_plan、flight_plan_verification、flight_plan_feedback、route、route_version |
| `airspace` | airspace、airspace_version、airspace_delivery |
| `device` | device、device_incident、ops_device、ops_device_maintenance_task、commission_task、commission_task_event（设备资料、故障、维护与调测） |
| `device_state` | device_state、ops_device_state、device_event_log（在线状态与设备事件，随每次上报变化） |
| `disposal` | disposal_authorization(_event)、disposal_emergency_stop、device_command |
| `tracking` | eo_tracking_task、eo_target_control（光电跟踪；跟踪期间每收到一次设备回报都更新） |
| `evidence` | evidence_file、evidence_link |
| `punishment` | punishment_case(_event)、handoff、handoff_delivery |
| `voice_recording` | advisory_voice_recording、advisory_voice_recording_setting（电话通知录音清单与当前选用，2026-10-06） |

`uav_auto_sms_task`、`uav_auto_voice_task` 是后台任务的租约与轮询记账，`alarm_merge_group` 是告警合并引擎的窗口状态，都没有页面读取，不纳入信号。

`V202610059002__realtime_topic_split.sql` 在 9001 之后拆出 `device_state` 并调整告警合并表的归属。实测模拟场景下设备每次上报都写在线状态，原先每分钟约 40 次 `device` 信号让只关心设备资料的页面跟着全量重读；拆分后 `device` 只在设备资料、故障、维护与调测变化时出现。

`V202610069022__advisory_voice_recording_realtime.sql`（2026-10-06）为电话通知录音两张表加 `voice_recording`；当前选用表 `advisory_voice_recording_setting` 另发 `alarm`，因为告警详情里的电话状态取决于有没有可播放的录音。后台管理端“接口配置 → 电话通知录音”订阅 `voice_recording`。见[电话通知录音管理](电话通知录音管理-2026-10-06.md)。

`V202610069041__realtime_tracking_topic.sql`（2026-10-06）把光电跟踪的两张表从 `disposal` 改到单独的 `tracking`：跟踪期间每秒多次更新 `eo_tracking_task`，原先每次都发 `disposal`，告警页、反制办理、证据页跟着反复重读处置进度，告警页不停重画（BUG-06）。这两张表只有光电跟踪面板读取，面板自己每 5 秒读一次，目前没有页面订阅 `tracking`。

反制指令无论成功、失败、取消、超时还是发布结果不明，结案时都会发 `DeviceCommandFinished`，由处置结算把授权改为已完成或失败；授权行一变就有 `disposal` 信号，页面据此更新（BUG-08，此前取消、超时和发布结果不明三条路径不发）。

## 前端接入

业务前台 `src/services/realtime.js` + `src/hooks/useRealtimeRefresh.js`，后台管理端 `src/services/realtime.js`（两者逻辑相同）。EventSource 不能带 Bearer 头，改用 fetch 读流；断线按 1、2、4……最长 30 秒退避重连。页面重读时保留筛选、分页、选中项和滚动位置，选中行本身变化时才重读详情；同一页两次重读至少间隔 1–3 秒（统计页 10 秒、大屏 5 秒），页面隐藏时不读，回到前台再补。页面只重读变化的那一部分：融合感知目标变化只读目标与尾迹，设备在线状态最多每 10 秒重读一次设备组。

### 连接恢复（BUG-07 / ZT-07）

- **看门狗**：后端每 20 秒发一次心跳。45 秒内既没有信号也没有心跳就主动断开、立即重连；连接请求本身迟迟没有答复也按同样时限处理。实测经 Vite 开发代理时，后端被 kill 后代理并不关闭浏览器这一端的连接，旧版前端会一直停在这条“活着”的空连接上。
- **恢复后全部重读**：重连成功（收到 `ready`）、浏览器重新联网（`online`）、页面在后台停留 60 秒以上回到前台、后端监听重连后发来的 `"*"`，都通知页面全部重读（`"*"`，`recovery` 标记），补上期间错过的变化。首次连上不重读（页面刚加载过）。
- **兜底重读**：推送连不上，或 `ready.listening=false`（后端没在监听数据库）时，每 15 秒通知一次 `"*"`；收到真正的 `change` 后停止。
- **会话**：推送接口答复 401 后不再用这个会话连接，也不兜底重读（重读只会得到 401）；业务前台在登录状态变化（`auth-access-change`）时、管理端在页面以新会话订阅时立即按新会话重连。
- **重读失败重试**（`useRealtimeRefresh`）：同一时刻只跑一次重读，期间来的信号合并成结束后的一次。页面的重读函数读取失败时要抛出错误：断网、超时、408、429、5xx 按 2、4、8……最长 30 秒退避再读同一批变化；401、403、404 等再读也不会好的错误不重试；恢复信号到来时立即再读，不等退避。已有数据的页面读失败时保留上次结果，并提示“自动刷新失败（原因），正在重试；下面是上次读到的……”，读成功后提示消失；原来就处于读取失败状态的页面在下一次信号或兜底时整页重读。

### 各页面要点

- **告警页（BUG-06）**：列表、详情、动作区仍由 HTML 字符串绘制，改为就地更新（业务前台 `src/ui/domPatch.js`）：行按 `data-row` 对齐，内容没变不动节点，变了只改文字和属性，“核实事件事实”等按钮在刷新时保持原节点，点得中；`<details>` 的展开由用户决定。列表两次重读至少间隔 2 秒，统计卡片最多每 10 秒一次，逐行处置进度最多每 10 秒一次（到点自动补上）。当前打开的告警：本行变了或恢复重读时静默重读详情；处置或移送变化时重读它的处置记录，反制做完后进度马上跟着变（BUG-08）。1 秒一次的处置建议读取只在页面要显示的内容变了时才重画。
- **反制办理（BUG-08）**：处置变化或恢复重读时，打开的详情无论是否还在当前列表里都静默重读；已批准、执行中的详情还随设备状态（`device_state`，至少间隔 5 秒）重读。
- **空域页（TC-RT-006 / ZT-07c）**：“稍后生效”没有数据变化、不会有信号，页面按已读到的时刻自己定时：当前版本的失效时间、暂无生效版本的空域最早的待生效时间、正在查看的空域各版本的起止时间、航线版本的起止时间，到点后 1 秒重读；后端仍按旧状态返回时每 3 秒再查，最多 10 次。实测上级下发 35 秒后生效的新空域、30 秒后生效的新版本，到点后 2–3 秒页面即显示为生效中、显示新高度。其他按时间变化的页面已有定时读取：飞行计划 30 秒、空域监测 10 秒、大屏 30 秒、态势页自有轮询。
- **态势页（ZT-09）**：各组数据按读取权限请求，与后端接口一致：目标与融合状态 `target:read`、告警 `alarm:read`、风险 `risk:read`、移送 `handoff:read`、设备 `devices.read`、设备事件 `monitoring.read`、飞行计划 `flight:read`、空域 `airspace:read`。没有权限的组不发请求、不报“刷新失败”，地图上这一类为空；后端答复 403 也按没有权限处理，登录或权限变化后重新判断。例如值班员没有 `monitoring.read`，不再请求 `/device-events`。
- **管理端设备实时监测（ZT-49 / TC-OPS-002）**：不再每 10 秒、每 2 秒定时轮询，随 `device`、`device_state` 信号重读总览、设备树、待处理告警和当前设备（至少间隔 2 秒），推送不可用时由兜底每 15 秒读一次。“暂停读数刷新”只停住当前设备的指标读数、雷达航迹、运行趋势和事件记录；设备上线离线、健康状态、心跳和告警照常更新（实测暂停时设备掉线 1 秒内显示离线）。运行趋势面板随 `device_state` 至少间隔 10 秒重读，另每分钟补读一次让统计时段跟上当前时间，暂停时都不读。

## 迁移改号

这两个迁移最初编号为 V202610040001、V202610040002，与 main 同日的 `db/migration` 迁移（回放设备类型、模拟器融合参数）撞号；2026-10-05 改为 V202610050001、V202610050002 后，又与 main 当晚新增的同号迁移（天气预报规则风险、规范化模拟输入）撞号。Flyway 同时加载 `db/migration` 和 `db/postgresql`，同一版本号出现两次就无法启动。

2026-10-06 起改为 V202610059001、V202610059002：序号用 9xxx，main 按日期从 0001 往上编，不会再撞。两个脚本都可重复执行（建触发器前先删同名触发器）。以后新增实时刷新迁移也用 9xxx 序号，例如 2026-10-06 的 V202610069041。

已有编译结果的检出（`server/target`）改号后要先 `mvn clean` 再启动：Maven 不删旧文件，`target/classes` 里留着旧编号的两个脚本，Flyway 会报 `Found more than one migration with version 202610050001`。

已按旧编号装过这两个迁移的库（只有分支测试库）启动前先删掉旧记录，Flyway 会补装 main 的迁移和改号后的两个：

```sql
DELETE FROM flyway_schema_history
 WHERE script IN ('V202610040001__realtime_data_change_notify.sql','V202610040002__realtime_topic_split.sql',
                  'V202610050001__realtime_data_change_notify.sql','V202610050002__realtime_topic_split.sql');
```
