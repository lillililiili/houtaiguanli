# 单位管理员与单位授权

2026-10-20 起用户确认，2026-10-21 调整为手动创建和分配角色；2026-10-22 起单位管理员直接继承单位已开放的全部权限。前台业务上限与后台管理授权分别由平台配置。

## 使用方式

平台管理员在“系统管理 → 用户管理”选中单位后，从单位操作菜单打开“单位授权”：

1. 指定本单位一名前台用户担任管理员。没有合适账号时，先通过正常新增用户流程建立账号。
2. 设置单位可用的前台菜单、模块能力和动作权限，管理员直接获得这些明确开放的权限，无需另建管理员角色。单位未开放的权限仍不可用；直接反制须单位显式授予 OP。
3. 为其他人员明确选择本单位角色。没有合适角色时，手动填写新角色名称、权限和动作，再分配给人员；新角色默认无权限，不自动复制原角色。选中的管理员免于此次角色分配，保留原人员绑定。
4. 按需开通管理员可用的后台管理功能。点击“保存并立即生效”，系统完成内部校验后直接保存，无需手工预览，也不再弹出第二次确认。受影响人员需要重新登录，业务数据范围变为“本单位”。

单位管理员使用同一个账号登录前后台：前台权限跟随单位业务上限，后台可维护“本单位人员”“本单位角色”、个人资料，并使用平台开通的运维功能。其原角色仅保留为人员绑定，不再限制在任期间的有效权限；不能修改单位授权或本人任命。人员列表显示“单位管理员（继承单位授权）”，“我的权限”直接列出当前实际可用功能。申请不能自审、设备范围、证据、时效等业务限制继续执行。

平台首次启用或调整单位权限均直接保存。一次保存内部先取得校验凭据，再提交同一单位、版本及请求内容；凭据绑定操作者和人员/角色/数据范围快照，十分钟内有效。校验失败、过期或并发变化时不继续提交，提示重新加载后再保存；网络或超时导致结果未知时先重新加载核对，不自动重试。保存期间禁止重复提交；等待校验时关闭弹窗或切换单位，不会继续提交旧请求。撤任不会取消单位纳管，也不会恢复原先的全部单位数据范围。首次启用须指定管理员，已有单位可明确撤任后由平台代管。

各单位角色独立，允许不同单位使用相同角色名称；全局角色继续由平台维护。单位管理员新建人员固定为前台用户、本单位和本单位数据范围。人员跨单位调动、管理员替换、单位授权由平台办理。撤任或替换时，离任人员须保留启用的本单位角色，或在同次保存中手动分配；不得退回全局角色权限。

## 权限与数据约定

- `user_type` 仍为 `FRONTEND` 或 `BACKEND`。单位管理员是附加身份，不属于 `ROLE-BACKEND`。
- `/api/v1/auth/me` 新增 `management_context`，包含 `mode`（`PLATFORM`、`UNIT`、`NONE`）、单位管理时的 `org_id`、管理菜单和管理操作码。原业务 `menu_keys`、`permission_codes` 返回用户实际可用的业务权限，不混入单位管理权限。
- 单位管理员使用 `unit-users`、`unit-roles` 管理菜单和 `unit-users.manage`、`unit-roles.manage` 管理操作码。管理身份由服务器查有效任命关系，客户端字段或请求头不能授予此身份。
- 有效单位管理员直接使用单位业务授权；其他纳管前台人员取角色与单位上限的交集。本单位范围不包含下级单位；身份、任命、所属单位和 OWN_ORG 范围须一致。管理员保留的原角色可为全局或本单位角色，不允许其他单位角色。
- 单位管理员只能维护本单位人员与角色。原平台接口继续要求平台后台身份，伪造单位、账号类型、角色编号或数据范围不能绕过。
- 收紧上限会裁剪单位角色中超出的授权，并撤销受影响会话；管理员始终跟随当前单位授权，重新扩大上限不会自动恢复普通人员角色中已取消的权限。
- 反制、设备及光电启动按真实执行人重新校验当前权限和范围；权限收回不能阻断已执行设备的计时停机、全关重试及回执处理。
- 自动规则使用已有受保护系统主体和 `RULE_COUNTER_V2` 授权链路，不参与单位人员纳管，也不能由单位管理员启用或重置密码。

## 接口与兼容

所有接口沿用 `/api/v1`、Bearer 会话、snake_case、字符串 ID、`{ok,data,error}`，写入沿用版本校验、幂等及追加审计。

| 接口 | 用途 |
| --- | --- |
| `GET /organizations/{orgId}/delegation` | 平台读取单位配置、管理员候选、纳管人员、本单位角色和可授权目录 |
| `POST /organizations/{orgId}/delegation/preview` | 保存时内部校验迁移与权限变化，取得绑定快照的凭据 |
| `PUT /organizations/{orgId}/delegation` | 平台提交与内部校验一致的配置 |
| `/unit-admin/users` | 单位管理员人员列表、创建及后续人员管理 |
| `/unit-admin/roles` | 单位管理员角色列表、创建及后续角色管理 |
| `/unit-admin/catalog` | 单位管理工作区读取本单位授权上限 |

单位管理接口从会话推导唯一管理单位，不开放跨单位查询参数。列表、计数、分页与详情使用相同单位范围，密码、会话和凭据不进入审计内容。

任命或启用均不自动生成角色。首次保存时，选中的管理员不必新建或重分配角色；其他原来使用全局角色的人员须明确选择本单位角色。原全局角色与历史记录保留，平台后台账号及自动规则系统主体不迁移。原“查看单位”只读基本资料入口不变。

追加迁移 `V202610220001` 撤销现有有效单位管理员的旧会话、更新权限版本并记录策略变更审计，不改单位权限、角色或人员绑定。新增 `UserResponse.unit_administrator` 仅用于展示任命身份，不接受客户端写入授权。

请求增加 `new_roles: [{client_key,name,description,permissions,actions}]`、`member_assignments: [{user_id,role_code?,new_role_key?}]`、`retire_role_codes: [code]`。人员分配使用已有角色编号或本次新角色的临时键，不能同时填写两个目标。省略新增角色不会创建任何角色；已纳管且绑定有效本单位角色的人员可保持原绑定。新定义与分配纳入内部快照校验、幂等和审计。

历史自动副本的清理须显式选择替代角色与迁移人员。后端校验来源证据、同单位归属以及每名人员迁移前后的实际菜单、模块和动作权限完全等价；清理时管理员任命与单位前后台授权保持不变，不同时更换管理员或修改单位上限，也不修改目标角色权限凑成相等。全部人员迁移后确认无引用才删除副本，任何一步失败整体回滚。历史业务材料和审计保持原样，迁移不会使已删除的源全局角色重新出现。

## 验证范围

功能交付须验证两个独立单位及下级单位隔离、管理员本人授权保护、平台旧接口防绕过、上限收紧和重新扩大、旧会话失效、内部校验过期与并发冲突、重复提交、角色同名及 PostgreSQL 升级路径。界面验证包括一次点击的校验/提交顺序、校验失败不提交、请求内容一致、切换单位/关闭后的旧请求阻断，以及提交结果未知时重新读取。

业务回归包括自动核实/通知/撤离、人工申请审批且不能自审、自动反制、设备停止与回执、移送、天气和鸟群风险。测试环境使用隔离数据库，真实运行服务保持 `app.dev-seed.enabled=false`。自动化测试与实际浏览器验收分别记录，不以测试通过代替真实场景已演练。
