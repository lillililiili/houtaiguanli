# 合法性研判统一目标类别（2026-09-29）

## 用户确认的范围

同一目标使用有效设备观测形成的当前统一类别。明确为无人机后参与合法性研判，不以是否匹配飞行计划为进入条件；鸟类等非无人机和类别待确认不进入当前无人机队列。类别改变后更新当前范围，保留既有研判、告警、复核与冻结材料。本轮不调整告警自动核实的 80% 条件，不变更反制授权或通知流程。

## 当前实现

- `AttributeSelector` 使用已关联到同一目标、在融合时间窗口内且类别权重为正的来源；未知类别不作为反对票，不要求来源数量达到某个门槛。有效明确类别有冲突时不选权重较高的一方冒充已确定结论，输出未知并记录 `CLASS_CONFLICT`。关联歧义中的观测保留原始数据和待处理记录，其类别暂不作为确定依据。
- 雷达 TCP 解码已经提供的 UAV/BIRD/PERSON/VEHICLE 标签进入融合类别；识别中、未识别及未确认标签保持未知。不根据数值猜测协议码，不生成置信度或坐标。
- 合法性引擎、当前列表、分页、统计使用同一类别投影：有 `target_attribute_selection` 时取融合类别（空值为未知）；统一目标缺少融合结果时为未知；尚未进入融合的旧目标保留其原有类别。没有把旧记录回填为已经融合确认。
- 类别改变时递增融合属性版本；同类别重复上报不因类别本身递增版本。后台调度同时核对观测时间、类别和版本，支持位置观测时间未改变时的类别重新确认，不把上一轮无人机结论当作新一轮已研判结果。调度继续要求有效的新鲜观测与生效规则；无有效观测不启动正式判断。
- 新研判保存当时类别和类别版本。类别改变后，旧记录可按原 ID 只读查询，不能继续确认、改判或转告警。历史未保存类别快照的记录不回填；其类别显示保留兼容读取，因此不能当作历史类别快照使用。
- 未知转无人机后自动调度，有无计划均走既有规则。无人机转鸟或未知只改变当前研判资格，不自动解除已有告警，不删除旧记录。

## 运行与失败处理

流程在后台运行，不由页面加载触发写入。规则失败、缺参数及观测过期沿用现有错误/不可判定处理，不伪造成功。现有人工类别修正及覆盖优先级保留，不新增所有目标必须人工确认的步骤。

用户后续要求开启自动研判，`local` 的 `app.fusion.enabled`、`app.rule-engine.enabled` 默认改为开启，仍支持环境变量显式关闭。融合每 500 毫秒领取接入观测，研判每 5 秒检查新鲜无人机及类别版本，页面离开后继续运行。直连雷达还要求 `app.fusion.live-promotion.enabled` 与已完成的设备归属、接入条件。配置开启不代表真实设备已经验收。融合缺少类别权重的设备不会被擅自赋予类别识别能力。现有生效合法性规则参数为 DEMO，真实来源只能得到参数未确认的不可判定结论；没有把参数改为 CONFIRMED，也未开启模拟许可、启动回放和其他自动处置。

迁移 `V202609290001` 仅追加 `rule_evaluation.recognition_class_code/recognition_revision` 两列，不回填旧记录；PostgreSQL 专用 `V202609290002` 保护这两个快照字段不被回写。API 字段名不变；`object_type_code` 在新研判详情中表示当次类别快照，当前无人机列表额外检查当前类别及版本是否仍一致。后端历史读取与业务前台共用同一读取服务。

## 验收范围

新增回归覆盖：单来源无人机、明确类别冲突、未知来源不压过明确来源、雷达类别映射、未知/鸟不回退首个来源类别、无计划无人机、相同位置时刻下的类别往返变化、重复输入、当前列表与统计一致、旧快照保留、过期观测不重新调度。PostgreSQL 用例在独立 `stage456_verify_*` 数据库随机 schema 中验证迁移、版本更新与读取查询，不使用业务库做测试。

本说明不宣称真实设备识别准确率，不将单元测试通过当作现场设备验收。
