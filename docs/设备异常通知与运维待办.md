# 设备异常通知与运维待办

更新：2026-09-17。旧版“仅生成运维待办”的说明由本轮独立再次通知及发送历史契约补充；真实渠道接入范围不变。验收结果见文末。

## 用户操作

业务前台的飞行计划设备检查列表、地图设备悬停卡片都使用“通知设备异常”。当前有异常或尚未关闭告警的设备才显示此操作；只有历史已关闭告警时保留信息，不发起新通知。

点击后，后端重新核对可见计划、可见设备、航线附近范围和设备异常事实，保存一条运维待办。页面得到 `task_id` 才提示成功。待办不是短信、邮件、外部消息或重启指令。

管理端进入“运维管理 → 设备实时监测 → 运维待办”查看。待办随监测总览的既有刷新节奏读取，也可手动刷新；支持待处理、已反馈、全部和分页。具备操作权限者填写处理结果后，待办进入“已反馈”，保留报告人、报告时刻、通知时设备状态及处理人/时刻/内容。此操作不关闭设备告警、不下发重启，也不把设备自动标成恢复。

## API 与权限

- `POST /api/v1/flight-plans/{planId}/device-maintenance-tasks`：请求 `{ "device_id": "设备ID" }`，带 `Idempotency-Key`（8–128 字符）。需要 `handoff:create`、`flight:read`、`devices.read`、`monitoring.read`；新建时读取附近检查还需 `route:read`。沿用已有独立通知权限，不给只读用户增加写权限。
- `GET /api/v1/device-maintenance-tasks?status=PENDING&page=1&size=20`：需要 `monitoring.read`；`status` 为 `PENDING/HANDLED/ALL`，页从 1 起，size 为 1–100。返回 `items/page/size/total`。
- `POST /api/v1/device-maintenance-tasks/{taskId}/handling`：请求 `{ "expected_version": 1, "note": "处理结果" }`，带幂等键，需要 `monitoring.read` + `monitoring.op`；处理结果为 2–1000 字。版本或状态变化返回 `409 MAINTENANCE_TASK_CHANGED`，同键重放沿用既有 `409 IDEMPOTENCY_REPLAY`。

所有接口沿用 Bearer 数据库会话、snake_case 和 `{ok,data,error}`。待办包含 `task_id/device_id/device_no/device_name/reason/connectivity/health_code/observed_at/last_heartbeat_at/simulated/status/reported_by_name/reported_at/handled_by_name/handled_at/handling_note/version/can_handle/reused`；可省略未知时间及未处理字段。`plan_id/plan_no` 仅在仍有该计划读取权限和范围时返回。

待办按上报计划的组织/区域限制数据范围，同时保留 MQTT 设备的显式归属限制；被逻辑删除的设备待办暂不展示，数据库记录保留。`can_handle` 是界面提示，提交仍重新校验权限、范围与版本。

同一计划、同一设备在未处理时仅有一条待办。设备行锁和 `active_key` 唯一约束共同控制并发。每个提交键与操作者、原请求对应的待办持久关联；相同键重试返回原结果，跨计划或设备复用键返回 409。再次点击创建接口且已有活跃待办时返回 `reused=true`，不再次发通知。已反馈后的设备仍异常可另行报告为新待办；原待办的再次通知接口禁止发送。所有写操作和审计在同一事务中。

## 部署前提

服务实现位于 `houtaiguanli/server`；业务前台和管理端必须连接这一个 API 与同一数据库。两个前端各自登录，不共享浏览器 sessionStorage 或复制令牌。

当前业务前台源码位于 `dongyiwurenji/dongying-vue`，Vite 代理默认连接 8081；管理端后端同为 8081。不要只把单个通知接口代理到另一个后端，否则前台登录会话与计划/设备 ID 会不一致。

部署时使用 `APP_API_PROXY_TARGET=http://127.0.0.1:8081 npm run dev`（在业务前台目录）或既有 `APP_PUBLIC_API_BASE_URL` 配置统一 API 地址，再重新登录。生产反向代理同理。该配置用于统一连接同一本地后台；本轮运行恢复情况见下方记录，未更换业务数据库。

新增迁移 `V202609150001__device_maintenance_tasks.sql` 创建待办与提交去重表；需由新版后台正常启动时应用。旧版本接口不存在会明确报错，不退回模拟成功。


## 再次通知与每次发送历史（2026-09-17）

同一设备待办的后续提醒使用独立接口，不再复用“创建待办”冒充重发：

`POST /api/v1/device-maintenance-tasks/{taskId}/notifications/resend`

请求体 `{ "expected_attempt_no": 1, "reason": "人工再次通知" }`，带 8–128 字符 `Idempotency-Key`。`reason` 可省略，默认“人工再次通知”，最长 500 字。沿用 `handoff:create`、`monitoring.read`、`devices.read`、`flight:read`，重新检查附近设备另需 `route:read`。操作返回完整 Task，既有消费者的原字段保留。

新增字段：

- `notification_attempts`：按 `attempt_no` 倒序排列；每次独立保存 `attempt_id/attempt_no/requested_at/requested_by_name/reason/recipient_snapshot/delivery_status/receipt_status/receipt_result/blocked_reason/submitted_at/delivered_at/acknowledged_at/outcome_state/historical`。所有时间为 epoch 毫秒，未知时间省略，不能拿提交时间填充送达或回执时间。
- `latest_notification_attempt_no`：并发校验版本；没有原通知资料时为 0。
- `can_resend_notification/resend_blocked_reason/resend_available_at`：待办、权限、最近结果和冷却资格，提交时仍重新校验当前设备。`resend_available_at` 为服务端计算的冷却结束时刻，不表示其他阻断自动消失。
- 原 `notification_delivery_status/notification_receipt_status/notification_blocked_reason/recipient_snapshot` 返回最近一次发送结果；历史全部在 `notification_attempts`。最近失败不能覆盖以前已送达的事实。后台和业务前台可显示“最近一次失败；此前已送达 N 次”。

`outcome_state` 区分 `NOT_SENT`（调用渠道前即被配置/模式阻断）、`COMPLETED`（明确送达或失败）、`SUBMITTED`（已交渠道待结果）、`UNKNOWN`（调用异常/未知响应或无法确认的旧记录）。后两项禁止盲目重发，只保留原记录核对入口；本轮没有增加人工伪造回执或自动把未知改成失败的操作。

每次发送按原设置 ID 重新核对当前配置并冻结新快照，旧快照保持不变；不允许在前端任意改接收对象。缺配置、正式通道未接通或 live 来源不满足既有模拟门禁时，保留明确 `NOT_SENT` 尝试，不调用渠道。只有已有 local/test 模拟环境、MOCK 配置、mock/replay 来源及模拟渠道均满足时才调用既有模拟适配器，不发送真实通知。

服务端最短冷却为 60 秒，可用 `app.device-maintenance.resend-cooldown-seconds` 增大。普通异常需有效观测，默认最大 300 秒，由 `app.device-maintenance.resend-observation-max-age-seconds` 配置；未来观测和过期检查均拒绝。当前服务端检查确认的 OFFLINE/DISABLED 持续异常不要求故障设备重新上报才能提醒。每次都重新确认同计划附近的同一设备、当前异常/未关闭告警及数据范围，不使用旧待办内容替代当前检查。

并发按设备锁＋`expected_attempt_no` 串行；调用渠道前先争用操作者级幂等键，防止相同键跨设备并发。成功后同键、同任务、同版本、同原因重试返回 `reused=true`，不再调用渠道。设备处理与再次通知共享设备锁；已处理任务不能重发。每次发送和审计一起提交。当前仅模拟适配器允许调用；未来真实适配器不能直接沿用事务内调用，需要独立可靠发送/对账机制。

明确拒绝且未追加发送的 409 错误：`MAINTENANCE_RESEND_BLOCKED`、`MAINTENANCE_NOTICE_CHANGED`、`DEVICE_NOT_NEAR_PLAN`、`MAINTENANCE_OBSERVATION_STALE`、`DEVICE_NOT_ABNORMAL`、`IDEMPOTENCY_KEY_REUSED`；保底幂等冲突可能返回 `IDEMPOTENCY_REPLAY`。前端显示阻断原因并刷新，不把已知拒绝混成网络结果未知。

## 迁移与历史保护

追加 `V202609170001__device_maintenance_notice_attempts.sql` 建立发送历史表，保留原通知摘要。该版本已被本地开发服务 devtools 自动重载应用，不能修改其校验和。后续 `V202609170002__preserve_unknown_legacy_maintenance_notice.sql` 只纠正 001 为“原任务所有通知资料均为空”生成的确定性占位；不删除原待办或任何有发送资料的旧记录。

有旧通知资料时仅按原有结果、接收快照和报告时刻保留一条 `historical=true` 记录，不补造旧送达/签收时间。完全缺少通知资料的旧待办保持无发送记录、结果未知，不能当成“已发送”或开放盲目再次发送。

## 本轮验证

以下为隔离模拟验收，不代表真实渠道验收。新增 H2 API 测试覆盖发送历史、快照变更、明确失败与既往送达共存、冷却、乐观版本、幂等、未知/发送中阻断、已处理阻断、设备异常/时效/范围、离线持续故障、真实通道门禁及权限；PostgreSQL 另覆盖同待办并发、跨设备同键并发和旧通知迁移。

最终验证：`bash mvnw -Dtest=DeviceMaintenanceNoticeApiTest,DirectoryApiTest,DirectoryScopeApiTest package` 通过，24 条测试、0 失败、0 错误、0 跳过；独立 PostgreSQL 测试库执行 `DeviceMaintenanceNoticePostgresTest` 通过，12 条测试、0 失败、0 错误、0 跳过，包含 001 → 002 升级。`git diff --check` 通过。测试仅使用模拟渠道；真实通知通道未验收。源码变更不自动等于稳定服务已部署。编译写入开发服务使用的 `target/classes` 曾触发 devtools 自动重载，后续由主任务停用旧热重载进程后统一恢复服务。
