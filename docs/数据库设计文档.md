# 数据库设计文档

版本：V1.1；日期：2026-09-03。

适用项目：东营无人机融合感知与低空安全管理平台。数据库基线为 PostgreSQL 16 / PostGIS 3.5，持久化使用 MyBatis，迁移使用 Flyway。

本文承接[后端开发基线](后端开发基线.md)和[后端项目规则](../server/AGENTS.md)，提供表设计、字段类型、关系、约束、索引、事务和分期迁移依据。V1/V2 为原有基础表，V3 已实现设备运维最小闭环，身份 RBAC 另有版本化迁移；其余章节仍为拟建设计，不表示数据库已部署到生产。

## 1. 设计范围与依据

- 当前结构以 [Flyway 迁移目录](../server/src/main/resources/db/migration)为准，V1/V2 历史迁移保持不可修改；设备运维由 `V3__device_operations.sql` 新增，雷达与四通道协议接入由 `V202609040003__live_device_protocols_and_radar_sensing.sql` 扩展。
- 业务对象来源于 [mock.js](../dongying-vue/public/assets/js/mock.js)、[case.js](../dongying-vue/public/assets/js/case.js)、[workbenchEvents.js](../dongying-vue/src/services/workbenchEvents.js)及基线中的 F1–F12；Mock 中的值不是生产初始化数据。
- 覆盖身份权限、设备、目标轨迹、计划空域、研判、三类事件、指令回执、通知、证据与审计。完整行政处罚办案、任务领取转派、SLA 和算法训练不在本版建表范围。
- 表结构是工程设计建议；设备枚举、外部报文、授权参数、真实组织、阈值和保管期限仍按基线 Q1–Q8 确认。不得将本稿的技术枚举解释为厂商协议。
- 不一次性创建所有拟建表；按第 11 节依赖和业务切片落地。上线前还须编写对应迁移 SQL、Mapper、接口契约和数据库测试。

## 2. 通用物理约定

### 2.1 类型、命名和字段记法

表名、列名使用小写 snake_case；主键命名 `<实体>_id`。不批量更名现有表，也不将前端展示编号直接当持久化主键。

| 记法 | PostgreSQL 类型/含义 | 约定 |
| --- | --- | --- |
| `ID` | `varchar(36)` | 新主键由服务端生成 UUID 字符串；兼容现有用户、会话和审计引用，不改为另一种 ID 体系 |
| `V(n)` | `varchar(n)` | 有长度边界的代码、名称或摘要 |
| `T` | `timestamptz` | 新业务时间存带时区时刻；服务端使用 Instant，展示时转换 Asia/Shanghai |
| `J` | `jsonb` | 仅存原始/扩展载荷、输入快照、参数；主键、状态、权限范围、常用筛选字段不得藏入 JSON |
| `P/L/A` | `geometry(Point/LineString/MultiPolygon,4326)` | 分别为点、航线、面；规范坐标为 WGS-84，不能仅改 SRID 冒充坐标转换 |
| `!` / `?` | NOT NULL / 可空 | 每个字段均标记；主键隐含非空，不用默认 0 或空串替代未知 |
| `M` 公共列 | `created_at T!`、`updated_at T!`、`version bigint! DEFAULT 0` | 拟建可修改表使用；`version >= 0`，应用按旧版本条件更新并递增 |
| `R` 公共列 | `created_at T!` | 拟建追加记录使用；不附带无意义的更新时间与软删除标记 |
| `B` 来源列 | `source_mode V(8)!` | 业务根记录标明 `mock/replay/live`；部署环境仍须隔离，不依赖字段实现环境隔离 |
| `S` 归属列 | `owner_org_id ID?`、`district_id ID?` | 分别 FK → app_org/app_district；未知归属仅授权的数据质量处理入口可见，不默认为全域可见 |

表内列出 M/R/B/S 表示实际包含上述公共字段；除此之外不自动追加公共列。新字段的工程代码通常用英文，展示层映射中文；现有 `app_user.status` 中文值与时间 BIGINT 保持原状。新业务 T 类型不改变既有 API 的 epoch 毫秒字段，DTO 必须明确线格式。

新表时间由应用统一时钟写入，不将 `updated_at` 自动更新视为 PostgreSQL 默认行为。原始时间不可靠时允许发生时间为空，接收时间仍必填，并记录缺失/时钟偏差原因。

所有 S 列都需要真实归属判定；子记录默认通过根对象继承访问范围，不自行扩权。同一事务关联的来源与业务记录必须属于允许的 source_mode；发现 mock/live 混用时拒绝写入。人员 ID 均引用 app_user.user_id；JSON 快照中的姓名只是当时展示值，不是身份凭据。

### 2.2 完整性和删除

- 表中“FK → 表”默认引用该表主键；指定列或复合键时以注明的键为准。除显式授权的关系维护外，业务 FK 默认 `ON DELETE RESTRICT`，不级联删除证据、回执、审计或历史。
- 固定技术状态使用 `varchar + CHECK`，方便后续迁移扩展；外部未知枚举保留原码和协议版本，不转成正常状态。
- 主键/唯一约束自带索引，不重复建立同列索引。FK 引用侧的查询索引需要单独规划；仅有 FK 不代表引用侧已有索引。
- CHECK 只保障本行取值，跨表一致性通过 FK/唯一键及事务用例保证；“已恢复必须存在通过的验证记录”等不能靠跨表 CHECK 实现。可空列的 CHECK 不等于 NOT NULL。[PostgreSQL 16 约束说明](https://www.postgresql.org/docs/16/ddl-constraints.html)
- 本版不对所有表添加 `deleted`。用户/角色/设备停用，历史记录保留；有明确保管政策后才执行受控清理。清理不能破坏仍需保管的引用。

## 4. 核心关系与权威状态

| 关系 | 基数 | 约束和语义 |
| --- | --- | --- |
| 组织 → 用户；角色 → 用户 | 1:N | 沿用当前单角色 role_code；本版不同时引入另一套多角色授权真源 |
| 用户 ↔ 组织/区域数据范围 | 1:N 范围授权 | 以完整“组织、区域”元组授权，不能分别取两个集合再交叉组合 |
| 设备 → 状态历史/异常实例 | 1:N | 同设备再次故障新建实例，不覆盖前次异常 |
| 来源 → 设备/目标来源映射 | 1:N | 外部 ID 的唯一性包含来源及必要会话范围 |
| 目标 → 轨迹 → 轨迹点 | 1:N → 1:N | 目标、来源轨迹会话和设备编号分开 |
| 航线/空域 → 版本；计划 → 航线版本 | 1:N；N:1 | 已使用版本保持不可变，不能让历史计划跟随当前航线漂移 |
| 无人机事项 → 告警/核实 → 处置记录 | 1:N；处置 0..1 | 属实才创建处置；误报不产生正式处置或处罚案件 |
| 事件索引 → 无人机事项/风险/设备异常 | 每种来源 0..1:1 | 索引恰好引用一种来源；不另存一套业务阶段 |
| 授权 → 授权明细 → 指令 → 回执 | 1:N；1:0..1；1:N | 一次人工授权可包含明确的多个后续步骤；每条指令有真实参数授权依据 |
| 事件 → 交接/通知 | 1:N | 交接记录、消息发送、送达及行政处罚结果不混为一个状态 |
| 文件 ↔ 业务对象 | N:M | 独立关联行及真实 FK；多个业务可引用同一文件 |

无人机核实结论取 `uav_event`，处置阶段取 `uav_disposal`，风险阶段取 `flight_risk`，设备异常阶段取 `device_incident`，设备状态取 `device_state`，指令执行结果取 `device_command`。工作台仅派生摘要；计数与图表从权限过滤后的同源业务数据计算。

## 5. 拟建业务表与字段字典

本节所有表均为拟建。字段长度为工程初值，厂商标识超长时应依据真实样本调整设计，不能截断后接入。技术状态详见第 6 节；协议码及业务阈值须由 Q1/Q2/Q6 确认。

## 6. 状态字典与迁移约束

以下为平台内部拟用枚举，前端保持中文展示；数据库 CHECK 控制取值，应用服务控制合法转换及关联条件。

| 对象 | 内部值/显示含义 | 迁移守卫 |
| --- | --- | --- |
| uav_event.verification_result | PENDING 待核实；CONFIRMED 属实；FALSE_ALARM 误报 | 首期只从 PENDING 核实；并发仅一次生效，核实记录与摘要一致；重开另行确认 |
| uav_disposal.stage | COUNTER_READY 待反制；COUNTER_RUNNING 反制执行中；INTERFERENCE_RUNNING 干扰执行中；HANDOFF_READY 待交接；HANDED_OFF 已交接 | 依次推进；失败保留当前阶段并记录阻断与失败指令，不增加“处罚办结”终态 |
| flight_risk.status | PENDING_VERIFICATION 待核验；PENDING_NOTIFICATION 待通知；NOTIFIED 已通知；EXCLUDED 已排除 | 待核验→待通知或已排除；待通知→已通知；发送达到确认成功标准才推进 |
| device_incident.stage | PENDING 待处理；PROCESSING 处理中；PENDING_VERIFICATION 待验证；RECOVERED 已恢复 | 指令成功才进入待验证；真实状态快照通过恢复校验才关闭，失败不标恢复 |
| device_state.connectivity | UNKNOWN 未知；ONLINE 在线；OFFLINE 离线；ABNORMAL 异常 | 待机不发射不等于离线/异常；has_alarm 是叠加属性；原始 work_state_code 独立保存 |
| device_command.status | QUEUED；SENT；ACCEPTED；SUCCEEDED；FAILED；TIMED_OUT；CANCELLED | 发送成功不等于执行成功；只有明确回执可确认执行；超时后迟到结果仍保留，按幂等对账更新；已发出指令不能仅本地取消就称设备已停 |
| notification.status | PENDING；SENT；ACCEPTED；DELIVERED；FAILED；TIMED_OUT | 各渠道支持哪些中间态由 Q4 确认；不推断设备或外部单位已完成办理 |
| evidence_file.status | PENDING；AVAILABLE；MISSING；CORRUPT；DESTROYED | 实际写入并完成校验后 AVAILABLE；缺失/损坏保留元数据和异常；DESTROYED 仅人工销毁写入，删除对象、保留元数据 |

前三类业务完成条件不相互替代。正常结果不代表每个中间态都必须被设备上报；允许认证的完成回执直接证明执行完成，但必须保存收到的事实与缺失环节，不虚构中间回执。各类重复请求、失败重试和迟到回执由用例明确处理，不能仅执行无条件 `UPDATE status`。

## 7. 现有可靠性与审计表的拟扩展

所有扩展使用新迁移；旧字段类型和当前接口不变。新增列采用可兼容的默认/可空策略，检查数据后再收紧约束。

| 表 | 拟增加字段 | 约束与迁移原则 |
| --- | --- | --- |
| `outbox_event` | `status V(16)! DEFAULT 'PENDING'`；`aggregate_type V(32)?`；`aggregate_id ID?`；`dedup_key V(128)?`；`lease_owner V(64)?`；`lease_token ID?`；`lease_until bigint?`；`max_attempts integer?` | status PENDING/PROCESSING/DONE/DEAD；非空 dedup_key UNIQUE；索引 (status, available_at)、lease_until；旧 processed_at 非空回填 DONE；aggregate 仅路由快照，指令/通知通过 attempt FK 追溯 |
| `inbox_message` | `source_id ID?` FK → integration_source；`payload_hash V(64)?`；`payload J?`；`status V(16)! DEFAULT 'RECEIVED'`；`processed_at bigint?`；`last_error text?`；`lease_token ID?`；`lease_until bigint?` | status RECEIVED/PROCESSING/DONE/FAILED；保留 UNIQUE (source, source_msg_id)；source 定义为不可变来源命名空间，包含协议要求的会话范围；相同键不同 hash 告警并隔离，不覆盖原报文 |
| `idempotency_request` | `operation_code V(96)?`；`status V(16)?`；`http_status integer?`；`completed_at bigint?`；`expire_at bigint?`；`lease_token ID?`；`lease_until bigint?` | 新请求规范化键见下文；RUNNING/SUCCEEDED/FAILED；记录原 HTTP 状态和响应；历史字段回填确认后收紧，不把旧空响应视为已成功 |
| `audit_log` | `result V(16)?`；`reason_code V(64)?`；`trace_id V(64)?`；`event_id ID?` FK → event_registry；`before_snapshot J?`；`after_snapshot J?`；`source_mode V(8)?` | 保留旧日志和旧 occurred_at；新用例明确成功/失败；未知账号登录允许 user_id 为空；不因补 FK 删除旧日志 |
| `app_session` | 暂不改变认证字段和存储类型 | 继续通过有效用户判断会话；角色权限变更按新 permission_version 校验，不持久缓存过期权限 |

幂等键的工程方案：新请求将“已认证 user_id、operation_code、客户端幂等键”进行无歧义编码后计算 SHA-256，作为现有 idem_key；request_hash 另算规范化业务参数。相同键不同参数返回冲突；不同用户/操作不会误用同一缓存响应。响应重放前再次校验当前身份、数据权限及结果对象，避免通过旧缓存绕过新权限。

RUNNING 需要租约与恢复逻辑，不能永久卡住。幂等记录过期策略未确认前不自动清理受控操作去重依据；即使缓存响应清理，authorization_item_id 的唯一指令关联仍阻止同一授权重复创建指令。

## 8. 事务、租约与一致性

### 8.1 关键事务边界

| 用例 | 一个本地事务内完成 | 外部行为与失败处理 |
| --- | --- | --- |
| 核实告警 | 条件更新 uav_event.version、插入核实记录；属实时唯一创建处置；写审计 | 误报不创建处置；冲突返回当前状态，不再推进 |
| 提交重启/联动 | 校验会话与状态、授权和参数；保存授权明细、唯一指令、Outbox、幂等结果和成功审计 | 数据库提交后由 Worker 发送；不能在事务里等待设备 |
| 消费执行回执 | 锁定/声明 Inbox 处理权；插回执、条件更新指令、推进合法业务阶段、写审计并标记 Inbox 完成 | 处理失败回滚业务修改并保留可重试 Inbox；重复完成消息不重复推进 |
| 验证设备恢复 | 锁定异常实例、读取最新状态及规则快照、追加验证记录；通过时关闭异常和写审计 | 不通过也保留验证结果与失败原因；不能只更新页面摘要 |
| 通知交接 | 唯一交接、通知、Outbox 与审计一致保存 | 实际送达后更新通知与源业务；网络失败保持未完成，重试复用原交接 |
| 文件入库 | 先登记 PENDING，再执行存储写入；核验成功后事务更新 AVAILABLE 并写关联/审计 | 文件存储不是数据库事务；中断保留待核验状态，通过核对/补偿处理孤立对象 |

“失败事件必须留痕”不等于在即将回滚的事务里插一条日志。登录失败计数、锁定与失败审计需要专门的持久化事务边界；当前 AuthService 的已知风险见基线 G2。没有复现测试前不宣称已经解决。

### 8.2 Worker 处理规则

1. 短事务内领取到期任务，记录唯一 lease_token 和租约期限，然后提交。并发消费者可使用 `FOR UPDATE SKIP LOCKED` 避免领取相同任务；该方式用于队列消费，不用于需要一致完整视图的业务查询。[PostgreSQL SELECT 锁定说明](https://www.postgresql.org/docs/16/sql-select.html)
2. 在事务外发送；更新任务结果时匹配 outbox_id 与 lease_token，过期 Worker 不得覆盖新领取者状态。记录每次尝试，而不是每次重试生成新逻辑指令。
3. 在“外部已执行、平台未记录”窗口仍可能再次发送。数据库租约不能保证物理设备恰好执行一次；必须依赖厂商幂等能力或状态查询对账。协议不支持时超时动作进入待人工确认，不盲目重发。
4. 最大重试、退避和回执时限由协议与运行条件确认；耗尽后保留 DEAD/失败记录并告警，不静默丢弃，也不直接标业务成功。

## 9. 索引、空间查询与容量

### 9.1 主要访问路径

| 查询 | 索引/限制 |
| --- | --- |
| 用户账号登录、会话解析 | 复用 app_user.account 唯一索引及 app_session 主键；会话清理由 expire_at 索引支持 |
| 按组织区域查看待办 | 业务根表 (owner_org_id, district_id, 状态, 业务时间 DESC, 主键)；event_registry 用三个来源唯一索引联表 |
| 设备历史与异常 | device_id + 时间 + 主键；历史列表限制时间窗，禁止一次返回全部快照 |
| 轨迹回放 | track_id + observed_at + point_id；发生时间未知的记录单独说明按 received_at 排序；限制轨迹数、时段和点数 |
| 指令超时、消息投递 | device_command(status, deadline_at)；Outbox(status, available_at)；租约过期扫描索引 |
| 通知/回执/证据链 | 父对象 ID + 时间；evidence_link 的每种对象引用各自建索引，不以扫描全部 JSON 反查 |
| 日志检索 | 复用 occurred_at/user_id；新增 (object_type, object_id, occurred_at)；按实际筛选补索引，禁止为每列无差别建索引 |

列表使用确定性排序并在同一范围下计算 total；大规模时间序列优先使用“时间、主键”游标，新增契约另行定义，不破坏既有 page/size 接口。索引最终以真实量级和 `EXPLAIN (ANALYZE, BUFFERS)` 在隔离环境验证，不把设计索引视为性能验收结果。

### 9.2 空间计算

- 标准几何存 EPSG:4326，位置来自真实 WGS-84 数据；未知坐标基准报文隔离。经纬度角度差不能直接作为米。
- 空域相交/包含使用 geometry 与相应 GiST 索引；距离米制计算使用 geography，例如 `ST_DWithin(location::geography, query_point::geography, radius_m)`，并为该表达式建立匹配的 GiST 索引。geometry 与 geography 索引不能假定互相替代。[PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html)
- geometry 只处理平面位置；AGL/AMSL 保持独立字段，缺少地形/基准不能用简单相减推导。边界点是否算侵入、航线走廊宽度含义与空间有效期由 Q6 确认。
- 不从未知/无效空间数据生成 POINT(0 0)，不把仅有行政区轮廓当作设备位置或空域业务边界。

### 9.3 首期不预设分区

首期采用普通表和有界查询，不在缺少 Q8 容量数据时增加时间分区复杂度。优先测量 track_point、device_state_history、Inbox 和 audit_log 的日增量。容量估算为：记录频率 × 活跃来源数 × 每日活跃秒数 × 实测单条记录及索引大小 × 保留天数；副本、WAL 和备份另计，不填虚构规模。

需要分区时单独评审迁移：PostgreSQL 分区表的主键/唯一约束必须包含分区键；不能直接把现有 point_id 单列主键或来源去重约束搬到时间分区表后声称仍全局唯一。保留独立未分区的 Inbox 去重索引，重新设计复合引用及数据搬迁。[PostgreSQL 16 分区限制](https://www.postgresql.org/docs/16/ddl-partitioning.html)

## 10. 数据安全、保管与未知信息

- 数据库应用账号只获得业务所需权限；迁移/扩展管理与日常运行身份分离。audit_log、回执等追加事实的更新/删除权限按实际业务最小化，数据库管理员仍是独立信任边界，不能宣称绝对防篡改。
- 口令只保存编码值；会话 token、设备凭据不写审计快照。原始消息和通知目的地址可能含敏感信息，按权限过滤与保管策略处理。
- 权限范围按同一行的组织/区域元组匹配；统计和导出使用同样过滤。归属未知不得以 null 通配全域；后台管理必须显式授权。
- 不设置默认“五年”等演示保留期限。轨迹、日志、回执、证据分别确认保留策略；文件冻结、开放业务引用和争议保管状态优先阻止清理，不能直接删时间分区绕开关联检查。
- 备份覆盖数据库与实际文件对象，记录同一恢复点的关联；必须验证恢复后证据定位、哈希、指令去重及审计可用性。备份周期和恢复目标待 Q8，不在文档中虚构已满足指标。
- 待确认项沿用基线 Q1–Q8，重点为来源消息唯一范围、真实授权、通知成功标准、异常合并、规则阈值、保留期限及容量。结构设计可先行，相关真实行为不可凭设计稿启用。

## 11. 分期迁移与兼容策略

下表是实施顺序，不预占 V3/V4 等迁移号。实际开发时检查迁移目录与并行工作后分配下一个版本；禁止编辑 V1/V2 或向本轮仓库写入建表脚本。

| 阶段 | 建设对象 | 兼容与验收重点 |
| --- | --- | --- |
| A：认证与权限 | app_org/app_district/app_role/app_permission、两类权限关系、access_change_record；app_user 增量列/外键 | 从现有实际角色码回填角色目录；未知组织不伪造。新增默认 NONE 会收紧访问，须在功能切换时显式授权并验收，不悄悄给予 ALL |
| B：设备最小闭环 | integration_source、设备/状态/异常/恢复验证；event_registry 初版仅 DEVICE 来源；授权指令、Outbox/Inbox/幂等所需扩展 | 初版索引表只 FK 指向已创建的 device_incident；后续再增 UAV/RISK 列并替换 CHECK，不引用尚未创建的表。Mock 与 live 分开验收 |
| C：感知、计划、告警与风险 | 目标轨迹、计划空间版本、研判、uav_event/alarm/处置/risk；扩展统一事件索引；交接通知 | 按被引用表→引用表顺序建表；分别验证三条状态链。计划/规则/文件等前序必需依据随切片落地，不等最后再补 |
| D：完整证据与查询 | evidence_file/link/access/hold、调测能力；统计工作台查询及必要索引 | 所需证据底座可提前；只有相应业务表存在后才增加 evidence_link 的对应 FK 分支。统计先直接查询，不凭空建重复 KPI 真值表 |

迁移采用“加列/加表 → 检查与回填 → 更新应用 → 验证 → 收紧约束”。添加 FK 或 NOT NULL 前先统计旧数据问题，不删除历史来让校验通过。新旧认证接口、ID 类型和 BIGINT 时间保持兼容；修改应用 Mapper 与 DTO 必须在同一切片协调。

上线前在隔离 PostgreSQL/PostGIS 从空库应用全部迁移，并从包含真实结构脱敏旧数据的 V1/V2 基线升级；准备数据库与文件备份、失败回退方案。应用可回退不代表数据库结构可以无损逆迁移，删除列/改类型须另行评审。

## 12. 数据库验收清单

- 六张已有表逐列与迁移一致；新增表的主键、FK、唯一范围和可空性可在 PostgreSQL 实际验证；本稿中的工程假设有确认记录。
- 重复账号、来源消息、授权指令、通知交接和证据关联按约束拒绝或幂等重放；相同来源键不同载荷不得覆盖原事实。
- 两人并发核实只生效一次；同一设备多次异常保留不同实例；错误或缺失回执不能推进成功；服务重启后可恢复处理中任务。
- 同一业务阶段、授权参数、审计及关联记录一致；失败登录计数与审计不会因返回 401 被回滚丢失。
- 超时后的迟到回执、租约过期 Worker、外部执行后断网和重复回放均有测试，不以数据库事务宣称设备恰好执行一次。
- 旧角色码、旧会话、中文用户状态和毫秒到期字段保持兼容；越权列表、统计、导出与证据下载被拒绝，未知归属不泄露。
- 坐标基准、米制距离、高度基准、无效几何及缺失事实测试通过；历史计划/研判不随当前版本被覆盖。
- 文件入库中断、文件缺失、哈希不符、冻结和清理阻断均可验证；元数据存在不能当作证据文件可用。
- H2 仅用于快速应用测试，不能代替 PostgreSQL/PostGIS 约束、锁、空间 SQL、分区和迁移验证；报告实际测试数量、执行环境及未验收项。

本文本轮只执行文档、引用与源码结构核对；数据库性能、DDL 可执行性、迁移兼容和业务闭环均尚未验收。
