# 单位档案与通知对象接口（2026-09-16）

## 当前切片与入口

后台管理端在 `ruoyi-ui` 的系统管理增加“单位档案”“通知对象配置”。业务前台只读当前计划关联、当次反馈/交接/自动短信/电话/运维通知的对象摘要。旧计划必须由具备管理权限的人根据来源原始资料明确关联；不按单位或飞手姓名自动猜测。`source_id` 仍是技术接入来源，`source_binding_id` 才是该来源的报送单位映射，`operator_org_id` 是实际运营单位，`pilot_contact_id` 是该运营单位的执行飞手。

本轮没有外部入站 `external_org_code` 自动消费入口。后台计划关联命令会真实写入计划并被现有业务发送流程使用。短信/电话正式通道尚未接通，API/SMS/VOICE 配置不能伪称实际送达；MOCK 仅在本地/测试环境及 mock/replay 来源下推进模拟回执。

## 目录接口与权限

统一前缀 `/api/v1`，成功响应为 `{data: ...}`。所有写请求带 `Idempotency-Key`；更新请求必须 `expected_version`，冲突返回 409。列表支持 `page`、`size`（1–100）和 `keyword`，返回 `items/page/size/total`。

| 资源 | 接口 | 补充参数/权限 |
|---|---|---|
| 单位 | GET/POST `/organization-profiles`；GET/PATCH `/{id}` | 读 organizations.read 或 notificationSettings.read；写 organizations.auth；新增单位须 ALL 范围 |
| 联系人 | GET/POST `/contacts`；GET/PATCH `/{id}` | 列表 org_id、enabled；写 organizations.auth |
| 来源单位映射 | GET/POST `/plan-source-bindings`；PATCH `/{id}` | 列表 org_id、source_id；写 organizations.auth |
| 目录选项 | GET `/directory-options` | kind=organizations/contacts/sources/users/plans，org_id；不依赖用户管理或飞行业务菜单 |
| 计划主体 | GET/PATCH `/flight-plans/{id}/subjects` | 读 organizations.read 或原 flight:read，保留原计划范围；写 organizations.auth 加计划范围 |
| 通知配置 | GET/POST `/notification-settings`；GET/PATCH `/{id}` | 列表 purpose；notificationSettings.read/auth |
| 配置影响 | GET `/notification-settings/{id}/diagnostics` | 当前可用性、阻断原因、历史数、待发数、关联计划数 |
| 计划运维历史 | GET `/flight-plans/{id}/device-maintenance-tasks` | device_id 可选，page/size；原 flight:read 和计划/设备范围，不依赖后台运维菜单 |

单位、联系人、来源映射与单位通知配置按当前账号的 ALL/ASSIGNED/NONE 数据范围过滤。ASSIGNED 使用 `app_user_data_scope.org_id`。联系人跨范围详情与写入返回 404；通知配置只读权限读取联系人时，电话脱敏，邮箱、账号、核验依据不返回。目录不创建账号、不增加角色权限、不改变用户数据范围。新权限只注册，由管理员明确配置。

单位字段：org_id、org_code、name、parent_id/parent_name、organization_type（REGULATOR/OPERATOR/SERVICE/OTHER）、address、credit_code、remarks、responsibilities、version 和关联计数。单位不增加停用入口。

联系人字段：contact_id、org_id/org_name、name、roles（PILOT/PLAN_LIAISON/UNIT_LIAISON/MAINTENANCE）、phone、email、可选 user_id/user_name、enabled、valid_until、verified_at、verification_basis、version 与 notification_count/pending_count/history_count。修改实际号码时后端无条件清空旧核验；先保存新号码，再提交新的核验时间与依据。停用联系人保留历史。

来源映射字段：binding_id、source_id/source_name、external_org_code、org_id/org_name、enabled、version。已被计划或通知配置引用的映射不能更换来源/单位，可停用；停用后计划摘要保留原关联并显示 PARTIAL，未来发送阻断。

计划主体 PATCH 字段：source_binding_id、operator_org_id、pilot_contact_id、expected_version、reason。来源映射必须来自该计划同一技术来源且有效；飞手必须属于运营单位、具有 PILOT 角色且有效。GET 返回 plan_id/plan_no、source_id/source_name、各关联 ID/名称、pilot_name（当前联系人姓名，原申报姓名仍在原 filing 字段）、脱敏 pilot_contact_hint、association_status、version、feedback_recipient。

## 通知用途与执行规则

| purpose | 对象 | 消费者 |
|---|---|---|
| RISK_NOTICE | 全局固定“上级”，仅 risk-superior 配置，禁止指定其他单位/联系人/范围 | 原风险交接状态机；旧 recipient_id 外键不改 |
| PLAN_FEEDBACK | 该计划来源映射对应的报送单位及配置端点，可选 PLAN_LIAISON | 原设备检查反馈；同 verification_id 防重；检查保存独立于通知配置 |
| ADVISORY_SMS | 全局渠道，实际对象来自当前事件精确匹配计划的执行飞手 | 原 AutoSms 后台任务，一事件一任务、稳定渠道幂等键 |
| ADVISORY_VOICE | 全局渠道，实际对象来自当前事件精确匹配计划的执行飞手 | 原 AutoVoice 后台任务，保留录音/接通/播放/未知结果守卫 |
| UAV_PUNISHMENT | 明确选择接收单位，独立 UNIT_LIAISON | 原处罚材料移交状态机 |
| DEVICE_MAINTENANCE | 明确配置接收单位，可选 MAINTENANCE；未传设置时仅在可见范围唯一启用对象时选择 | 原设备异常待办；通知失败不影响待办 PENDING，不代表已处理或恢复 |

联系人角色、停用、有效期、配置有效期、来源关联在未来发送时重新检查。飞手还需要核验过的号码。事件必须满足既有目标/当前研判/数据时效/状态守卫；显式匹配同事件、同目标、同范围、最新 ACTIVE 研判的计划才可取飞手。单位联系人或登录账号不能兜底。领取任务前最终接收对象无效立即阻断。接收人、联系人版本或配置版本变更后，不能沿用旧渠道幂等键把重试发送给新对象。

通知配置字段为 purpose、recipient_org_id、contact_id、source_binding_id、channel_type（NONE/MOCK/API/SMS/VOICE）、endpoint_ref、enabled、valid_until、expected_version。RISK_NOTICE/ADVISORY_SMS/ADVISORY_VOICE 三个全局用途只 PATCH 预置配置，禁止 POST 多个配置。endpoint_ref 仅部署端点标识，不是任意 URL、号码或凭据。

固定模板 `template_code/template_version` 与既有 `receipt_requirement` 只读返回，并冻结到快照；本轮没有新增模板编辑系统。

## 快照与历史

`recipient_snapshot` 包含 recipient_id/recipient_name、org_id/org_name、contact_id/contact_name/contact_hint、channel_type、endpoint_ref、setting_id、config_version、contact_version、configured、blocked_reason（中文说明）、captured_at、template_code/template_version、receipt_requirement。只有新任务/新提交生成快照；旧记录保持 NULL，明确“当时未采集”，不以当前联系人回填过去。

计划 workflow 的 recipient_snapshot 为当前对象，feedback[].recipient_snapshot 为当次提交历史；handoff detail 的 recipient_snapshot 与 recipient_name_snapshot 固定历史。运维 Task 追加 recipient_snapshot、notification_delivery_status、notification_receipt_status、notification_blocked_reason。短信和语音 auto_sms/auto_voice 各自追加 recipient_snapshot：本渠道任务冻结优先，尚未尝试发送且没有快照时才解析本用途当前对象；旧任务已发送尝试却无快照则返回 NULL，不回填历史；records[] 保留各条记录自身快照。顶层 recipient 只代表当前明确关联飞手，不借用短信历史代表电话对象。

迁移仅 `V202609160004__organization_contact_notification.sql`、`V202609160005__directory_notification_consumers.sql`，不回写旧交接材料、旧反馈、旧短信或电话接收事实。
