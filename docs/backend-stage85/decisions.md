# 阶段 8.5（设备直连切片）自动决策记录

领导按"推荐选项自动决策、阶段提交后汇报"的模式记录。上游依据：决策 8-30（凌云被移除、云端只保留本平台）、契约 `docs/backend-stage8/device-direct-access-contract.md` v1.1。

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| 8.5-1 | 凌云三路（AOA/DCD/RID）进 `source_type_catalog` 但 `schema_status=DEMO`，`spec_ref` 指向协议 A v8.6 | 字段有出处但未联调；CONFIRMED 只在真实设备联调通过后改 |
| 8.5-2 | `fusion_config demo-v1` 的 JSON 由迁移 070 整体重写而非局部 UPDATE | H2 与 PG 没有共同的 JSON 局部更新语法；重写内容与 050 逐字一致，只增三项精度与三项权重 |
| 8.5-3 | AOA 的权重 `position=0`、`motion=0`，只参与身份 | 协议 A 明确 AOA 只给方位（extension.direction），不给可用位置 |
| 8.5-4 | 冻结接口 `SourceEstimate`/`TargetState` 通过"追加字段 + 保留旧签名构造器"扩展 | 旧构造器调用点 3 + 10 处跨 E1/E2/助手文件，重写会破坏文件独占 |
| 8.5-5 | 飞手位置在融合层取"身份主源"的 `pilot*`，落 `target_latest_state.pilot_location` | C02-6 需要目标级而非观测级的飞手位置；身份主源（TDOA/DCD/RID）是唯一携带该字段的来源 |
| 8.5-6 | `C02.bvlos_distance_m` 作为新 DEMO 参数（500 m）追加到 LEGALITY-DEMO v1/v2 | 与 legacy demo 的超视距阈值一致；代码不出现裸阈值 |
| 8.5-7 | 凌云 `altitude` 只落 `quality.altitude_raw`，`altitude_amsl_m/height_agl_m` 记 `REFERENCE_UNKNOWN` | 高度基准（海拔 vs 椭球高）客户尚未答复；未知不补默认值 |
| 8.5-8 | 协议 C 的引导源 `objectData` 不入库，只记 `quality.bootstrap_source_*` | 引导源是别的传感器的观测，入库会造成同一观测两次计入关联 |
| 8.5-9 | `live-radar:` 前缀是否被 `claim` 领取由 `app.fusion.live-promotion.enabled` 决定 | 用户裁定实测雷达提升缺省关；关闭时 ops 模型不变 |
| 8.5-10 | 前端只改 `labels.js` 字典，不改任何 `.vue` | 用户约束"不随意改之前的页面，只接数据" |
| 8.5-11 | 迁移 070 的参数 UPDATE 只按 `config_version='demo-v1'` 匹配，不带 `status/version` 条件 | 审查 P1-1：激活/停用会递增 `version`，带条件会在演示库上静默匹配 0 行 |
| 8.5-12 | C02-6 超视距复用既有参数 `C02-6.vlos_m`（500 m，DEMO），**不新增** `bvlos_distance_m`，迁移 072 取消 | E2 指出 `rule_code='C02'` 引擎查不到、迁移插 `rule_param` 会撞种子期才存在的版本行外键；既有 `vlos_m` 含义相同、已在种子/测试桩/契约目录里，零共享改动 |
| 8.5-13 | 实测雷达提升端口只写 `inbox_message` 信封（`live-radar:<device_id>`），映射留给管线的 `LiveRadarFrameMapper` | 实测与回放走同一条管线，幂等/租约/毒帧计数只有一份实现；与"只落 inbox 不写业务表"一致 |
| 8.5-14 | 实测端口只接受已在 `integration_source` 注册且启用的设备，不自动建来源行 | `source_type/schema_status` 只有注册流程知道；未注册设备的数据不得混进统一目标库 |
| 8.5-15 | `NoopSourceObservationPort` 归 8.5.3，与实测端口按 `app.fusion.live-promotion.enabled` 严格互斥，删除原"开关打开即抛异常"死代码 | 两个 `@Component` 同时注册会让开关打开时上下文启动失败 |
| 8.5-16 | `FusionInboxRepository.claim` 的前缀白名单：`replay:`/`lingyun:`/`eo-edge:` 固定；`live-radar:` 仅在 `livePromotion.enabled=true` 时加入 | 开关关闭时连领都不领，避免 `fusion_attempts` 被推到上限后帧被永久判为毒帧 |
| 8.5-17 | E2 为接通飞手位置/类别来源字段而改的五处共享文件（`LegalityEvaluationService`、`TargetReadService`、`FusionReadService`、`FusedTrackRepository`、`ObservationReadRepository`）认可为 8.5.2 范围 | 都只是把新字段接上，无既有语义改动，且不在 E1/助手独占清单内 |
| 8.5-18 | C02-6 三态细化：有飞手位置但目标位置缺失 → UNDETERMINED `POSITION_UNKNOWN`；`target_latest_state.pilot_location` 每帧重写（含写回 NULL） | 不拿单边坐标硬算；飞手位置描述"此刻"，留旧值会用过期位置判超视距 |
| 8.5-19 | 实测端口对 `SOURCE_MESSAGE_CONFLICT`（同键不同哈希）单独捕获、单独计数、ERROR 级告警，且不覆盖已存信封 | 先到的信封才是当时真正收到的证据；冲突混在普通拒收里会淹没真实的上游故障 |
| 8.5-20 | 协议 C（光电边端）`external_target_id` 与 `source_session_key` 同取 `taskId` | 协议未给光电自己的目标号；对齐文档 §5.2 "一个跟踪任务一条 link"；厂家给独立目标号时再改（会影响已建立 link 的身份，届时记决策） |
| 8.5-21 | 协议 A 帧级 `observed_at` 取首个对象的 `time`，不一致的对象另记 `quality.observed_at_raw`；逐对象时刻不在本期 | 逐对象 `observed_at` 需改 `FusionPipeline` 的关联预测口径，超出切片范围 |
| 8.5-22 | 协议 C 未映射的新事件类型返回空帧、inbox 记 DONE 而非 FAILED | 协作者 A 新增事件类型不应把 inbox 刷成 FAILED；空帧不产观测即无副作用 |
| 8.5-23 | 数据集 v2 的 inbox `payload` 就是设备原样报文，`payload_hash` 由 `loadV2()` 直接计算、不经 `FusionReplayReader` 复算；v1 读取路径不变 | 库里存的必须是设备原文；哈希一致性由助手在 PG 专项用 `sha256(payload)` 复核 |
| 8.5-24 | 凌云高度的 `REFERENCE_UNKNOWN` 标记落在 `quality.altitude_datum`，两个高度数值列留空 | 数值列放不下标记；契约 §3/§6 文本同步 |
| 8.5-25 | 协议 A 一帧内出现第二个不同的 `taskId` → 整帧 FAILED，原因 `MIXED_TASK_ID`，不拆帧、不并 link | 会话键参与 link 身份，把两个跟踪任务并成一条 link 是静默错误；映射不猜，先按"一帧一任务"前提拦下并让协作者 A 可见（审查 P2-4） |
| 8.5-26 | 阶段 8 的 `ProductionStage8SeedIsolationTest` 与 `Stage8AccessControlServiceTest` 目录断言由五行改为八行（预期漂移，不放宽其它断言） | 迁移 070 登记 AOA/DCD/RID，目录仍要求仅 RADAR CONFIRMED |
| 8.5-27 | 提交后跟进（E2）：`writeSelection` 在帧内无任何来源时跳过 upsert 保留上一帧归属；飞手位置只由携带身份主源的帧改写（身份主源在但未报 pilot → 写 NULL；整帧无身份主源 → 不碰该列） | 无源帧把三列刷成 NULL 读起来像"从来不知道"；同毫秒 TDOA/EO 帧顺序不再决定飞手位置去留，与位置列"保留最后可信点"的原则对齐 |
| 8.5-28 | `target_latest_state` 增 `pilot_observed_at`（迁移 072，E2），C02-6 facts 输出该时间；本期不设独立"飞手位置过期"阈值，过期性由目标整体新鲜度（C03 `fresh_seconds`）兜底，写进契约 | 可保留的飞手位置需要可追溯的时刻；新增阈值又要走 rule_param 种子路径，留待联调后按真实数据定 |
| 8.5-29 | 提交后跟进（E1）：`inbox_message` 增单调写入序列 `ingest_seq`（迁移 073，`BIGINT GENERATED BY DEFAULT AS IDENTITY`，H2/PG 皆可），`claim`/`failExhausted` 排序改 `received_at ASC, ingest_seq ASC`；另加"同毫秒一批帧打乱顺序处理两遍结果一致"的用例 | 现排序键 `inbox_id` 是随机 UUID，v2 数据集每帧多源同毫秒，处理顺序每次灌库都可能不同；`source_msg_id` 是跨来源不可比的 VARCHAR。排序键只买可复现，顺序无关性需要用例单独钉 |
| 8.5-30 | `pilot_location` 与 `pilot_observed_at` "同写同留"由 `upsertLatestState` 保证，本期不加 `IS NULL` 对等的库层 CHECK | 助手指出 `LatestState` 的 15 参夹具构造器允许只写位置；改成硬约束需先改 E2 的夹具构造器，留待联调后一并处理 |
