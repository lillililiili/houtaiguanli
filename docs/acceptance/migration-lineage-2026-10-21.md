# 2026-10-21 独立功能迁移历史兼容

本次合并的两个分支各自使用了 `202610200001`、`202610200002`：本地分支用于显示数据清理及单位分权，远端分支用于反制模式及空域生命周期。已应用迁移不能改名、改内容、改校验值或执行 `repair`。

## 历史选择与升级

`MigrationLineage.configure(...)` 继续先识别 20261016 的自动/人工通知历史，再独立识别 20261020 的功能历史。原文件仅按历史分组移动，文件名、字节内容及 Java 迁移类名保持。

| 历史 | 原迁移解析位置 | 新兼容迁移补齐内容 |
| --- | --- | --- |
| 空库或本地单位分权历史 | `db/lineage/features-local`；PostgreSQL 追加 `features-local-postgresql`；保留原单位 Java 迁移 | 反制模式、空域生命周期 |
| 远端反制模式/空域历史 | `db/lineage/features-remote`；排除原本地单位 Java 迁移 | 单位分权、K03 预测结构及触发器、WGS84 申报字段、录音用途、单位后台授权、角色历史来源 |

新迁移 `V202610210002__reconcile_independent_feature_histories` 在两个旧历史版本之后补齐缺失结构。远端历史下，原 `V202610210001__unit_role_copy_origin` 不会提前执行；它在兼容迁移内部、单位表和权限结构完成后执行，避免引用尚不存在的单位字段。不会伪造另一分支的旧 Flyway 历史行。

选择器同时核验成功状态、原脚本名称及原校验值。未知、失败、混合历史直接拒绝升级，保留数据库供核查；不能改历史来绕过检查。两组 SQL 不得同时扫描。

## 运行方式

Spring Boot 由现有 Flyway 定制器统一调用选择器。独立工具或测试升级既有数据库时，也必须在 `load()` 前调用 `MigrationLineage.configure(configuration)`，不能直接扫描默认目录后调用 `migrate()`。部署保留 PostgreSQL 资源目录以及各历史目录，不能删除目前没有选中的分支文件。

升级不启用开发种子、不调整运行库规则、不迁移人员角色、不扩大单位权限，也不改写历史空域版本和业务归属。原始显示名清理及角色来源证据仅沿用原迁移既定处理。

## 自动验证

`FeatureMigrationLineagePostgresTest` 在随机隔离 schema 中应用完整的空库、本地及远端旧迁移，再升级至当前版本，检查：

- 原 Flyway 每行记录保持，二次启动迁移数为零且校验通过。
- 反制、空域、单位分权、K03 触发器、WGS84 和后台授权结构均完整。
- 兼容 SQL 明确按 UTF-8 读取，K03 的两类中文来源名称与原文一致。
- 存量人员的单位、角色、范围、权限版本及角色记录不变。
- 未知校验和、混合分支在兼容迁移执行前被拒绝。

既有 `MigrationLineagePostgresTest` 继续覆盖 20261016 两个历史升级；`LocalAirspaceMigrationPostgresTest` 验证旧空域版本和来源不被改写。实际执行结果以本轮独立测试产物为准，不以测试存在代替通过。
