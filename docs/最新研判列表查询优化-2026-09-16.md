# 最新研判列表查询优化（2026-09-16）

## 问题与数据口径

本地业务库共有 29,141 条研判历史，其中 replay 29,065 条、mock 76 条；回放来自 47 个目标持续更新的观测，不代表两万多架无人机。修复前 ACTIVE 最新列表返回 95 条，统计查询实测约 19.482 秒，超过前台既有 15 秒等待上限；完整接口也发生过 20/60 秒超时。

执行计划显示旧 `NOT EXISTS` 把 TARGET 和 PLAN 关联放进同一个 OR，只能先按主体类型聚合后反复比较历史。另有数据库进程异常退出并恢复的日志；本次查询优化不声称解决该异常退出的底层原因。

## 实现及兼容边界

`LegalityEvaluationReadRepository.where()` 将 TARGET 和 PLAN 的最新记录检查拆成两条 `NOT EXISTS`，分别按 target_id、plan_id 与 mode 等值匹配。仍以 evaluated_at、evaluation_id 降序选择最新，保留缺少主体引用的历史语义。

状态、时间、来源、规则版本和权限范围不被提前塞进“查找更新记录”的子查询，避免新记录不满足筛选时让旧记录重新变成最新。count 和 list 继续共享同一条件；响应、分页、权限、复核及告警关联均不变。

此次只改查询，不新增表、索引或迁移。研判频率、历史记录和前台超时设置保持不变。后台管理前端没有直接调用该列表，已有角色菜单描述仍保留；业务前台 `legalityApi.listEvaluations` 与后端统计聚合继续使用原契约。

## 验证

- 修复前先运行新增 PostgreSQL 回归：结果一致性通过，3 万条历史的统计和列表合计约 138.976 秒，超过 5 秒验收线，性能测试失败。
- 修复后 `Stage7PostgresTest` 10 项、`LegalityReviewApiTest` 10 项、`RuleEffectApiTest` 2 项，共 22 项通过，失败/错误/跳过均为 0。PostgreSQL 测试使用专用 `stage456_verify_s7` 库下随机 schema；自动应用迁移并清理该测试 schema，不把测试记录写入日常业务库。
- 新增语义测试覆盖 TARGET/PLAN 相互隔离、ACTIVE/SHADOW、相同时间按 ID 选择、空目标引用、最新结论与状态过滤、分页、授权范围外新记录不让旧记录回流、完整历史读取。性能测试创建 50 个目标各 600 条历史，加基础记录共 30,001 条；查询合计必须小于 5 秒，单次 SQL 同时有 5 秒取消上限。整个测试方法耗时包含建数据，不能拿它当接口耗时。
- 本地 PostgreSQL 对照统计查询由约 19.482 秒降到约 0.445 秒。重启后完整接口多次采样约 0.22–1.82 秒；最后一次 size=10/20/100 分别为 277/221/359 毫秒，total 均为 95，最后一页大小实际返回 95 条。采样受缓存、并发和本机环境影响，不作为生产 SLA。
- 真实业务前台完成登录、研判列表读取、页面刷新、目标研判深链及关联告警的飞手短信卡片展示。最后一次从导航到列表可见约 1.755 秒，页面脚本错误、研判失败响应、测试发起的业务写请求均为 0。无业务数据拦截或模拟响应；未发送短信或下发设备指令。
- 后端打包通过，已重启本地 local 服务，健康状态 UP；业务库历史仍为 29,141 条。未发布到远端环境。
